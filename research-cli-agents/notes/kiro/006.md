# 006 — Context engineering: memory, compaction, and tool clearing
- **Source**: https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools (Anthropic, 2026-03)
- **Claim**: Three first-party API primitives — compaction, tool-result clearing, and memory — each target a different kind of context growth for long-horizon agents; a worked research-agent example shows how to pick and combine them. Context has diminishing marginal returns ("context rot"), so the discipline is keeping the smallest set of high-signal tokens.
- **Mechanism**: Compaction (`compact_20260112`, beta `compact-2026-01-12`) distills the whole transcript into a lossy summary when a token threshold is crossed (default trigger 150K, server-side min 50K; configurable `instructions` fully replace the default summary prompt). Tool-result clearing (`clear_tool_uses_20250919`, beta `context-management-2025-06-27`) surgically replaces old `tool_result` blocks with a placeholder while keeping the `tool_use` record (default trigger 100K, `keep` default 3 tool uses, `clear_at_least`, `exclude_tools`); no inference cost but invalidates cached prefixes. Memory (`memory_20250818`) is model-driven file-backed note-taking (view/create/str_replace/insert/delete/rename) persisting across sessions; client implements the storage backend. Mental model: compaction compresses the whole window, clearing drops stale re-fetchable data inside it, memory moves info out of the window to survive resets.
- **Numbers**: Corpus = 8 synthetic docs ~40K tokens each, ~328,955 total (~320K of tool-result volume). Model claude-sonnet-5-5 (SDK 0.109.0), 1M-token window; earlier models cap at 200K. Baseline run peaked 335,279 tokens over 5 turns; file-read results = 322,946 tokens = 96.3% of final context. On 200K window baseline hard-stopped after 3 turns at 168,242 tokens. Compaction run: trigger 180K, peak 169,164 → final 5,829 tokens after a ~2,783-token summary (high-level facts 3/3 preserved, obscure appendix specifics 0/3). Clearing run: trigger 30K, keep=4, clear_at_least 10K; peak 173,137 (vs baseline 335,279), 4 clearing events freeing ~163K tokens each; 7 of 8 reads cleared. Demo clear: 128,740 → 43,060 tokens (67% reduction, keep=1 of 3). Demo compact: 741 → 449 tokens (39%). Memory: Session-2 without memory peaked 333,977 tokens / 8 reads; with memory 172,623 / 4 reads. Gemini-style cache hits up to 10× cheaper (cited elsewhere).
- **Token-cost implication**: Diagnose which bottleneck you actually have before adding config. Use clearing (cheapest, lossless-by-refetch) when the window is dominated by re-fetchable tool results; use compaction when non-refetchable dialogue/reasoning bloats the window (but expect loss of verbatim specifics); use memory for cross-session persistence. Set `clear_at_least` high enough to make cache invalidation worthwhile. Customize the compaction `instructions` to name at-risk specifics (e.g., every quantitative figure). Combine all three with clearing/compaction splitting work (higher trigger, keep=6) and `exclude_tools` for memory.
- **Caveats**: Vendor doc from Anthropic promoting its own API primitives; synthetic corpus, single task, illustrative not benchmarked. Compaction is lossy by design (loses exact numbers/phrasing). Clearing may force re-reads (cost depends on tool); multi-fire `show_cleared_reads` can misclassify re-read files. Memory handler is a demo (prod needs size caps, path-traversal guards shown). Token buckets use char/4 estimates scaled to API totals. Claude Code is cited as running compaction + two memory systems in production.
