# 069 — Coding agents usually can't price on outcomes. Ours can.
- **Source**: https://sourcegraph.com/blog/agentic-batch-changes-pricing (Sourcegraph, 2026-07)
- **Claim**: Sourcegraph's Agentic Batch Changes prices on outcomes — you only pay when a changeset it generates is merged into your codebase; if it isn't merged, you don't pay. This contrasts with the industry norm of per-token (effort) pricing.
- **Mechanism**: A special-purpose agent scoped deliberately in its harness, system prompt, permissions, and tools to one concrete problem (large-scale migrations/changes across repos). Because it's narrow, it can minimize cost at scale — e.g. a single agent generating a thousand-case switch statement instead of deploying a thousand agents, and not reaching for a coding agent when a script will do. This bounded cost structure is what lets them bill on merged outcomes rather than compute. General-purpose agents can't do this because their openness makes ROI unanswerable.
- **Numbers**: Canva beta: 50+ pull requests raised and merged across repos in a library migration; billed on the 50+ merged PRs, not the ones opened or hours spent. (No per-token prices or percentages given.) Mentions Sierra, Fin, Decagon as examples of per-resolution pricing in other verticals.
- **Token-cost implication**: Outcome-based pricing aligns vendor incentives with the buyer and makes spend countable against a merged artifact rather than a compute forecast or seat. Builders can scope narrow, special-purpose agents (tight harness/prompt/tools) and prefer scripts/single-agent code generation over fan-out agent swarms to make per-task cost predictable enough to guarantee.
- **Caveats**: Vendor marketing post; single named beta customer (self-reported testimonial). No cost figures, token counts, or independent measurement. "Produced PRs is cheap; following through is the hard part" is an assertion. Scope limited to migration-style batch changes, not general coding.
