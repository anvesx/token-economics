# 007 — Shedding Heavy Memories: Context Compaction in Codex, Claude Code, and OpenCode
- **Source**: https://justin3go.com/en/posts/2026/04/09-context-compaction-in-codex-claude-code-and-opencode (justin3go, 2026-04)
- **Claim**: Compares how three CLI agents compact context on a 26-message, ~15,400-token login-bug session; Claude Code's layered, cache-preserving approach avoids most LLM summary calls.
- **Mechanism**: Codex: LLM writes a handoff summary replacing history; keeps user messages verbatim (recent user messages capped ~20,000 tokens), deletes assistant/tool messages; local path (compact.rs) or remote responses/compact endpoint (OpenAI only); falls back to head trimming. Claude Code (reverse-engineered, not open source): L1 replaces old tool results with "[Old tool result content cleared]" with zero LLM cost; L2 avoids altering the message prefix to keep prompt-cache hits; L3 tries Session Memory Compact first, else a 9-section structured LLM summary, then re-reads up to 5 recent files; reactive compaction on prompt_too_long; pauses after 3 failures. OpenCode: prune by timestamp-hiding (not deleting) only if >20,000 tokens freed, protecting latest 40,000 tokens and last 2 user turns, never pruning skill outputs; then hidden-agent 5-heading summary and replays last user message.
- **Numbers**: Session ~15,400 tokens; 5 tool results ~12,500 tokens (81%). Claude Code auto-compact threshold = effective window minus 13,000 tokens (effective = window minus min(max output, 20,000)); re-read budget 50,000 tokens total, 5,000 per file.
- **Token-cost implication**: Clear stale tool outputs first, keep the prompt prefix stable to preserve cache hits, and use LLM summarization only as a last resort; tool results dominate context.
- **Caveats**: Blog analysis; Claude Code details from community reverse engineering and unofficial leaked source; token figures are estimates for a constructed scenario, no measured cost comparison.
- **Topic**: compression
