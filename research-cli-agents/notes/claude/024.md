# 024 — Token Reduction Is Not Cost Reduction: end-to-end efficiency of API-based coding agents
- **Source**: https://arxiv.org/abs/2607.12161 (arXiv, PointFive authors Weinberger and Hozez, 2026-07)
- **Claim**: Cutting delivered tool-output tokens does not cut the bill for Claude Code. The most aggressive compressor (RTK-ML) removed 38.4% of tool-output tokens but raised billed cost 6.8% (paired CI +2.8 to +11.3). Per-task correlation between token reduction and cost change is only r=0.154 [-0.051, +0.356] over 100 Haiku tasks.
- **Mechanism**: Cost is dominated by the cached prefix that is re-read every turn, not by tool output. Attribution of cost: harness base (system prompt plus tool definitions) 74.7%, hidden thinking plus residual 19.4%, tool outputs 3.3%, tool-call args 1.4%, retrieved files 0.8%, conversation history 0.5%. User-visible tokens total about 6%, so visible-token compression has a ceiling near 5%. RTK-ML's 38.4% cut equals about 1.3% of total cost. Compression also changes the trajectory: later first edit (+0.94 turns), more post-edit retrieval re-entries (+0.32 per run), more repeated-search tokens (+301 per run), and every extra turn re-transmits the cached prefix. A first-turn token costs about 1.60x versus 1.25x for a last-turn token. Headroom proxy added about 49% more cache-read context by the first edit (38.7k vs 25.9k median).
- **Numbers**: Campaign: 2,908 runs executed, 2,848 analyzed, 103 tasks, 7 repos, Haiku 4.5, Sonnet 5, Opus 4.8, 4 arms (baseline Claude Code 2.1.201, RTK v0.44.1, RTK-ML, Headroom v0.27.0). Bill split: cache creation 44.3%, cache reads 35.4%, output 10.4%, uncached input 1.3%, unattributed 8.7%. Pricing used: cache write 1.25x input (5-minute TTL), cache read 0.1x. Baseline success 96.2%, 4.46 turns. Cost change vs baseline: RTK -2.7% [-5.6, -0.1] (holdout only -2.3% [-7.4, +2.1]), RTK-ML +6.8%, Headroom +48.4% [+42.3, +55.0] (+67% on Opus 4.8; positive in every model-effort cell and every task family). Cost per successful run ratio: RTK 0.968, RTK-ML 1.051, Headroom 1.464. Long sessions: RTK -1.3% n.s., Headroom +60.9%. Opus medium-effort RTK replication: -0.1% [-9.3, +7.8]. Codex replication (gpt-5.6-luna, 40 task pairs): Headroom -12.49% reconstructed cost at equal success but wall time +238%, so the sign flips by harness. Single-shot Go study: compression cut billable tokens 73% and cost 59% but patch apply fell 27/40 to 15/40; byte-exact grounding restored apply 31% to 83%. Pytest rule: 31.9% savings at 56.1% marker recall, fixed to 15.3% savings at 99.2% recall.
- **Token-cost implication**: Do not adopt an output compressor or proxy on token-count savings. Measure cost per successful run end to end. The lever is the fixed prefix (system prompt, tool definitions, cache behavior) and turn count, not tool-output size. RTK is roughly neutral to slightly positive; proxy layers like Headroom raised Claude Code cost by about half. Never compress dense evidence (tracebacks, test output, edit anchors); piping compressed search output into shell counting commands gave silently wrong answers (gates-on success 93.3% vs 100%).
- **Caveats**: Vendor study (PointFive), only "pre-specified", no public preregistration. Cache carryover between arms is a validity threat (median gap 10.8 s, inside the 5-minute TTL), checked but not ruled out. Baseline success 96-98% limits sensitivity; effective sample about 38-45 tasks per arm; Opus and effort cells are small and exploratory. Token counts are local-tokenizer estimates. Phase labels come from a deterministic classifier, not human judges. Quality dimensions beyond test pass (maintainability, review effort) were not measured. Source text in the corpus ends mid-section (about 90k characters), so the benchmark-design recommendations and appendices were not read.
