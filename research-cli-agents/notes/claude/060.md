# 060 — 5 ways to cut Claude Code costs with LiteLLM
- **Source**: https://docs.litellm.ai/blog/save-claude-code-costs-with-litellm (LiteLLM, 2026-07-04)
- **Claim**: A platform admin running a LiteLLM proxy in front of Claude Code can cut cost with five server-side levers and no client changes.
- **Mechanism**: (1) Budget windows (`budget_limits` with max_budget and budget_duration, stackable e.g. $10/24h and $100/30d) plus per-model `model_max_budget` and `budget_fallbacks` chains that reroute Opus to Sonnet to Haiku when a model budget is exhausted. (2) Automatic prompt caching: `cache_control_injection_points` inserts the cache marker on the system message or second-to-last user turn; `prompt_caching` pre-call check routes to the deployment used first. (3) Headroom compression sidecar as a pre_call guardrail rewrites tool outputs, file reads and RAG payloads, with `retrieve_headroom` to fetch originals. (4) `mcp_tool_search_enabled` replaces the tool catalog with two virtual tools (`mcp_tool_search`, `mcp_tool_call`); ranking is token overlap over name+description, no embeddings. (5) Auto routing: Semantic, Complexity (rule-based tiers SIMPLE/MEDIUM/COMPLEX/REASONING) or Adaptive (beta).
- **Numbers**: Cache hit costs roughly 10% of a fresh input token. Headroom reported savings 60-95% on the compressible portion of Claude Code traffic. Example budgets: Opus $20/day, Sonnet $10/day, Haiku $5/day; key budgets $10/day and $100/month. No end-to-end savings figure for the stacked levers.
- **Token-cost implication**: Put cost controls at a gateway: cap spend with fallbacks, inject cache markers, compress tool output, defer MCP tools and route by complexity, all without touching developer machines.
- **Caveats**: Vendor blog promoting its own product; the 60-95% figure is "reported" with no source or methodology; no measured stacked savings; example router config uses non-Anthropic models for a Claude Code workload.
- **Topic**: routing
