# 051 — How to Add Prompt Caching to an Anthropic SDK App and Measure the Hit Rate
- **Source**: https://startdebugging.net/2026/04/how-to-add-prompt-caching-to-an-anthropic-sdk-app-and-measure-the-hit-rate (Start Debugging, 2026-04-29)
- **Claim**: Marking stable prefixes with cache_control cuts repeated input tokens to 10% of base price; the post shows breakpoint placement for agent loops and a wrapper to compute hit rate and cost from the usage object.
- **Mechanism**: cache_control {"type":"ephemeral"} (optional ttl "5m" or "1h") on a block caches everything before and including it, if the prefix matches byte-for-byte; up to 4 explicit breakpoints (tools, system, repo summary, recent turn), ordered stable to volatile. system must be an array of blocks, not a string. Longer TTL entries must precede shorter. Breakpoint looks back at most 20 blocks. Read usage fields cache_creation_input_tokens, cache_read_input_tokens, input_tokens. Automatic top-level cache_control picks one breakpoint.
- **Numbers**: Read 0.10x base; 5m write 1.25x; 1h write 2.0x. Minimum cacheable prefix: Opus 4.7 4,096 tokens; Sonnet 4.6 2,048; Haiku 4.5 4,096; older Sonnet 4.5/Opus 4.1/Sonnet 3.7 1,024. Sonnet 4.6 $3/MTok input, $15 output; Opus 4.7 $15 input, $75 output. Example: 8k prefix costs $0.024/turn uncached, $0.0024 cached; 50 turns = $1.20 uncached prefix. Break-even reads (m-1)/0.9: 0.28 (5m), 1.11 (1h). ~85ms latency saved on cached prefix. Typical 50-turn Sonnet 4.6 agent: 95-98% hit on system block, 70-90% on messages, 1.5x-4x lower total spend. Caches isolated per organization and, as of Feb 2026, per workspace.
- **Token-cost implication**: Always cache system prompt and tool catalog; keep timestamps, IDs and tool ordering deterministic; add breakpoints near the tail in long tool loops; use 1h TTL for bursty traffic; track hit rate yourself.
- **Caveats**: Third-party blog (site states it uses an AI agent for writing); hit-rate and 1.5-4x figures are "typical" without a stated measurement; model pricing and minimums are as quoted by the blog, not verified here; claims "5x to 10x" input reduction elsewhere in the post.
