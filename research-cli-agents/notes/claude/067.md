# 067 — Context Editing Looks Like a Feature. It's Actually a Garbage Collector Without Write Barriers
- **Source**: https://conikeec.substack.com/p/context-editing-looks-like-a-feature (Chetan Conikee, Substack, 2026-02-11)
- **Claim**: Anthropic's context editing and compaction mutate an agent's working memory mid-reasoning, like a garbage collector with no write barriers, and can silently drop information the agent still depends on. Safe use needs liveness heuristics, safe points and finalization.
- **Mechanism**: Context editing (beta header context-management-2025-06-27): clear_tool_uses_20250919 drops old tool results beyond a token threshold keeping N most recent (exclude_tools protects some); clear_thinking_20251015 clears thinking blocks; cleared content is replaced by placeholder text. Compaction (compact_20260112) has the model summarise earlier history and replaces it; pause_after_compaction returns stop_reason "compaction" so the harness can inspect or augment the summary. Claude Code plan mode's "clear context and auto-accept edits" is the stop-the-world case; cited GitHub issues #20797 (orphaned tasks), #18878 (multi-problem context lost), #18599 (destructive default), #19530 (clears despite opt-out). Proposed safeguards: root-set heuristics, dynamic dependency marking, clear only at safe points, finalize before clearing, never collect mid-composition, crystallise findings into artifacts first.
- **Numbers**: none (illustrative scenario: clear at turn 20 keeping the 3 most recent tool results)
- **Token-cost implication**: Context clearing cuts cost but trades off correctness; harnesses should persist key results externally, use exclude_tools and pause_after_compaction, and expect re-read costs when old results are cleared.
- **Caveats**: Opinion essay with analogy, no experiments or token measurements; relies on user-reported GitHub issues. A comment promotes a competing product.
- **Topic**: compression
