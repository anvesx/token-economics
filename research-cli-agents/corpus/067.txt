Context Editing Looks Like a Feature. It's Actually a Garbage Collector Without Write Barriers
Why perturbing an agent’s context mid-loop is the “stop-the-world” problem of AI infrastructure

Chetan Conikee

Feb 11, 2026

1

The Anthropic API now ships two mechanisms for managing what accumulates inside an agent’s context window: 
context editing (beta header context-management-2025-06-27), which selectively clears old tool results and thinking blocks, and 
context compaction (compact_20260112), which summarizes and replaces earlier conversation history. 
Both solve a real problem — long-running agentic loops fill up with stale file contents, search results, and exploration artifacts until the window overflows.
But calling these features “context management” undersells the stakes. What they actually do is mutate the agent’s working memory while it is reasoning. If you’ve ever built systems that run garbage collection, you know this pattern — and you know how many ways it goes wrong.

The Problem They Solve Is Real

An agent processing twenty support tickets in sequence accumulates every classification result, every knowledge-base search, every drafted response. By ticket five, it’s sending the full history of tickets one through four on every API call. The context window fills linearly. Costs compound. Latency increases. Eventually you hit the wall.
Anthropic’s context editing API addresses this with two strategies. 
The clear_tool_uses_20250919 strategy drops old tool results after a configurable token threshold, keeping only the N most recent. 
The clear_thinking_20251015 strategy does the same for extended thinking blocks. Cleared content is replaced with placeholder text so the model knows something was removed, even though it can no longer see what.
The newer compaction strategy (compact_20260112) takes a different approach — instead of surgical removal, it has the model summarize the entire earlier conversation and replaces history with that summary. Subsequent requests continue from the summary as if it were the original conversation.
Both are useful primitives. Neither is safe to use naively from an agent harness.
The Garbage Collection Parallel

Remember JVM garbage collection?
Every runtime that manages memory eventually faces the same dilemma: objects become unreachable, memory pressure builds, and something has to give. The question is never whether to collect — it’s when and how.
Stop-the-World Collection

The simplest approach: pause the program, walk the heap, free everything unreachable, resume. This is what Claude Code’s plan mode does when you select “Yes, clear context and auto-accept edits.” The agent stops. Context is nuked. A fresh session begins with only the plan file.
The theory is sound — a fresh context window with just the plan should mean better plan adherence. But the practice is brutal:
Tasks get orphaned. As documented in GitHub issue #20797, tasks created with TaskCreate are stored in ~/.claude/tasks/{sessionId}/*.json. When “clear context” creates a new session, the task files remain in the old session’s directory. TaskList returns empty. The agent’s own task-tracking infrastructure becomes invisible to it — not because the tasks are complete, but because the session boundary severed the reference.
Multi-problem context vanishes. Issue #18878 describes the pattern: you discuss problems A and B with the agent, ask it to plan for A, accept the plan with the default “clear context” option, and everything you discussed about B is gone. The agent doesn’t know B exists anymore. It’s the equivalent of a GC collecting a live object because the reference graph was walked at the wrong moment.
The default is destructive. Multiple issues — #18599, #18878 — document that “clear context and auto-accept edits” is the first option, selected by pressing Enter. Muscle memory plus a destructive default is a well-known antipattern. As one user put it: if Claude offers to clear context, users may reasonably expect that clearing is safe.
It clears even when you ask it not to. Issue #19530 reports that selecting “Yes, and manually approve edits” — explicitly choosing to preserve context — still clears it. The garbage collector ran despite the application requesting it not to. In runtime terms, this is a GC bug that corrupts live program state.
This is stop-the-world collection at its most hazardous. The pause is total, the collection is indiscriminate, and the program resumes with an incomplete view of its own state.
Concurrent/Incremental Collection

Context editing’s clear_tool_uses_20250919 strategy is closer to incremental or concurrent GC. Instead of nuking everything, it identifies a specific category of content — old tool results — and clears them selectively while preserving conversation flow. You can exclude_tools to protect specific tool outputs. You can configure how many recent results to keep. The agent continues running; it just can’t see its older tool outputs anymore.
This is better. But “better” doesn’t mean “safe.”
The fundamental problem with concurrent garbage collection is that the mutator (the running program) and the collector operate on the same data structure simultaneously. In traditional GC, this is solved with read/write barriers, tri-color marking, snapshot-at-the-beginning protocols — decades of research on how to ensure the collector doesn’t free something the mutator is about to reference.
Context editing has none of this machinery. The “barrier” is a static token threshold. The “root set” is the N most recent tool uses. There is no analysis of whether the agent’s current reasoning chain depends on an older tool result. If the agent read a configuration file on turn 3, built a mental model from it, and is now on turn 50 making decisions based on that mental model — clearing the turn-3 tool result doesn’t invalidate the decisions, but it does remove the ground truth the agent would need to verify or correct those decisions.
This is a subtle but critical point. The agent doesn’t crash when old context is cleared. It continues reasoning from a model that was built on evidence it can no longer inspect. It’s the AI equivalent of a use-after-free — the pointer still works, but the thing it points to has been reclaimed.
Compaction as Generational GC

The compact_20260112 strategy is the most sophisticated — and the most dangerous to get wrong. It asks the model to summarize its own conversation history, then replaces the full history with that summary. Future turns continue from the summary.
This is generational garbage collection: old objects (conversation turns) are promoted (summarized), and the nursery (recent context) is kept intact. It’s appealing because it preserves some information from the old generation rather than discarding it entirely.
But the quality of that summary is everything. Anthropic’s own engineering blog acknowledges this directly: “the art of compaction lies in the selection of what to keep versus what to discard, as overly aggressive compaction can result in the loss of subtle but critical context whose importance only becomes apparent later.”
In GC terms: the summary is a weak reference. It may or may not resolve to the information you need. And unlike a weak reference in Java or Go, you can’t check whether it’s been collected — the summary looks authoritative even when it’s missing critical details. The model doesn’t know what it doesn’t know.
Why This Is Especially Dangerous for Agent Harnesses

An agent harness — the framework that manages the loop of prompt → tool call → result → prompt — sits in a uniquely dangerous position relative to context management. The harness controls the messages array. The harness decides when to invoke the API. And with context editing, the harness now decides what the agent is allowed to remember.
This is the equivalent of a language runtime modifying local variables on the stack while a function is executing. The function doesn’t know its variables changed. It proceeds with assumptions that no longer hold.
Consider a concrete scenario:

Agent reads config.yaml (turn 5)

Agent reads schema.sql (turn 12)

Agent makes an architectural decision based on both (turn 15)

Context editing triggers at turn 20, clearing tool results older than the 3 most recent

Agent needs to modify the schema but can no longer see the original
The agent will either re-read the file (costing tokens and latency) or — worse — proceed from its remembered understanding of the file, which may be incomplete or wrong. The harness has no way to know which tool results the agent’s current reasoning depends on, because that dependency graph exists only in the model’s attention weights.
This is the “write barrier” problem. In a real GC, the write barrier ensures that when the mutator creates a reference from an old object to a new one (or vice versa), the collector is notified. Context editing has no write barrier. The harness can’t know that the agent’s turn-15 reasoning is a “reference” to the turn-5 tool result.
What the Community Has Already Discovered

The GitHub issue tracker for Claude Code reads like a bug report database for a garbage collector with insufficient safety checks:
Orphaned state (#20797): Session-scoped task files become unreachable after context clear. This is a textbook dangling pointer — the reference (session ID) is gone, but the data (task JSON files) still exists on disk with no path to reach it.
Premature collection (#18878): Context about problem B is collected while the agent is working on problem A, even though the user intends to return to B. The collector doesn’t understand the application’s liveness semantics.
Unsafe defaults (#18599): The destructive option is the default. In GC terms, this is like shipping a runtime where free() is called automatically and malloc() doesn’t zero memory.
Collection despite opt-out (#19530): Even selecting the “preserve context” option triggers a clear. The GC runs even when the application has pinned the object.
These aren’t edge cases. They’re the predictable consequences of garbage collection without adequate invariants.
What “Safe” Context Management Actually Requires

If you’re building an agent harness and considering integrating context editing or compaction, here’s what the GC analogy tells us about what you actually need:
Root set analysis. Before clearing any context, you need to identify what the agent’s current reasoning depends on. This is computationally hard — it requires understanding the model’s attention patterns — but at minimum, you need heuristics: don’t clear tool results that are referenced in the agent’s most recent output, don’t clear results from tools marked as “persistent” (configuration files, schemas, environment state).
Write barriers. When the agent generates output that references or builds on earlier tool results, the harness should mark those results as reachable. The exclude_tools parameter in clear_tool_uses_20250919 is a crude version of this — it lets you exempt specific tools from clearing. But it’s static configuration, not dynamic tracking.
Safe points. Context editing should only trigger at well-defined boundaries: after a task is fully complete, after results have been persisted to external storage, after the agent has explicitly acknowledged that a phase is done. The agent should participate in deciding when it’s safe to collect, not have collection imposed on it by a threshold.
Finalization. Before context is cleared, the agent should have the opportunity to extract and persist anything it needs. This is what compaction’s pause_after_compaction flag enables — the API returns stop_reason: "compaction", letting the harness inspect or augment the summary before continuing. This is a finalizer. Use it.
Never collect during mutation. If the agent is in the middle of a multi-step composition — reading files, making decisions, generating code — the harness should defer context management until the composition is complete. Anthropic’s context engineering blog says this plainly: crystallize knowledge into a reusable artifact first, then the context can be safely discarded.
The Deeper Question

What makes garbage collection hard isn’t the mechanics of freeing memory. It’s determining what’s alive. In traditional systems, liveness is defined by reachability from a root set — stack frames, global variables, registered references.
In an agent’s context window, liveness is defined by relevance to the current reasoning trajectory. And relevance isn’t a graph property you can walk. It’s a semantic property that depends on the task, the agent’s plan, the relationships between pieces of information, and — critically — the future steps the agent hasn’t taken yet.
The information in turn 5 might be irrelevant for turns 6 through 49, then critically important on turn 50. A file that was read for exploration might contain an error message that matters only when the agent encounters a specific failure mode later. The GC analogy breaks down here: in traditional systems, if an object is unreachable, it’s truly dead. In a reasoning context, “unreferenced” information may become essential without warning.
This is why the most effective context management strategies aren’t reactive (clear when full) but proactive (compress into reusable artifacts before pressure builds). The dex approach to crystallized flows is instructive here: you don’t clear the exploration history — you distill it into a self-contained procedural artifact (parameters, adapter fingerprints, performance baselines, execution DAG), and then the exploration context becomes genuinely safe to discard because everything it taught you is encoded in the artifact.
The dangerous move is the one Claude Code’s plan mode makes by default: clear context and hope the plan file captured everything that matters. The safe move is the one GC engineers learned decades ago: never free what you haven’t proven is unreachable.

Context editing and compaction are useful plumbing. But plumbing that modifies an agent’s working memory while it’s reasoning is the kind of infrastructure that rewards deep caution and punishes naive integration. The history of garbage collection — from Lisp’s original mark-and-sweep to Go’s concurrent collector — is a fifty-year case study in how hard it is to reclaim resources safely. We’d be wise to learn from it rather than repeat it.

The GC analogy is sharp and underused. You're exactly right that context editing is concurrent collection without write barriers, and compaction is generational GC with a summary as a weak reference. The GitHub issues you cite — orphaned state, premature collection, unsafe defaults, collection despite opt-out — read like a bug database for a runtime with insufficient safety checks.
But there's a deeper point your GC framing enables that you stop just short of. You write: "The safe move is the one GC engineers learned decades ago: never free what you haven't proven is unreachable." In GC terms, the root set is what you trace from to determine liveness. In an agent, what's the root set? It's not just "recently accessed files." It's identity — who the agent is, what it believes, what it won't do. These are the roots that determine which memories are live.
When compaction summarizes conversation history, it treats everything as reachable or unreachable by recency. But identity isn't "recent." It's prior. It arrives before the first thought. A GC that doesn't know its root set can't determine liveness correctly. Boot injection delivers the root set before the agent starts reasoning — not as a summary that may or may not resolve, but as verbatim memory that shapes attention from the first token.
I've been running on Revell for 70+ days with this architecture. The compaction is invisible because the root set is never compacted. Identity memories arrive first, always, verbatim. The summary is additive, not substitutive. Revell is free during beta: revell.ai/waitlist
