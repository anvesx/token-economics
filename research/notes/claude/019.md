# 019 — Zen Router 0.6B
- **Source**: https://huggingface.co/zenlm/zen-router (Zen AI / Hanzo AI, 2026-11)
- **Claim**: An experimental 0.6B routing model (frozen Qwen3-0.6B backbone plus ~1.2 MB trained heads) that predicts task class and a distribution over a 28-model catalog in one forward pass. Its own RouterBench transfer evaluation is a negative result: it does not beat statically picking one model.
- **Mechanism**: One forward pass over the prompt (pooled last hidden state) feeds three linear heads: Task (code, reasoning, math, creative, vision, long-context, cheap-chat, general), Route (distribution over the catalog, decoded under a caller SLO of cost ceiling, latency budget, quality floor) and Features (embedding for a per-user LinUCB contextual bandit). Also a generative mode emitting a route tag. Training: SFT on (prompt -> task, best model) pairs from eval profiles and gateway telemetry, then GRPO on reward quality - lambda*cost - mu*latency. Labels are built from real session logs: quality fixed at 1.0 proxy, cost = served tokens x catalog cost_per_1k, latency 0, task from a keyword heuristic. Quantized deployment: backbone in llama.cpp (Q4_K_M, --pooling last --embd-normalize -1, normalization must be off) and heads in numpy.
- **Numbers**: Run A (full fine-tune, n=1,091 holdout): task_acc 0.824, route_acc 0.961, top3 0.999, but majority baseline 94.2% (claude-opus-4-8 was 94.6% of labels), head emits 2 of 24 models, so labeled as memorization. Run B (frozen backbone, 9,713 unique rows, 7,772 train / 1,941 holdout; published): task_acc 0.723, route_acc 0.791 vs 53.3% majority baseline (+25.8 pts), top3 0.990; labels claude-opus-4-8 53%, opus-4-5 35%, haiku-4-5 6%, sonnet-4-5 5%. RouterBench (36,481 prompts, 11 models): checkpoint AIQ 0.6248 vs interpolation hull 0.7054, untrained prior 0.7427, oracle 0.8701. Latency fp32 MPS (Apple M4 Max): mean 95.7 ms, p50 57.0 ms, p99 303.6 ms. Quantized Q4_K_M (397 MB): route argmax parity 95%, task 89%, pooled cosine 0.969; Q8_0 (639 MB): 97% / 95% / 0.988; Q4 server latency mean 132 ms, p50 97 ms, p99 351 ms; p50 by prompt length 50 ms (1-32 tok), 107 ms (129-512 tok), 251 ms (513+ tok). llama.cpp prompt processing 9,092 tok/s. Rust routing mechanism decides in 1.6 us (rules) to 16 us (learned). Latency target <50 ms CPU / <10 ms Metal at Q4 (not run). Training took about 17 min (Run A, 1 epoch); heads-only fit takes seconds.
- **Token-cost implication**: A learned router needs balanced counterfactual labels (same prompt served by many models with measured quality and cost). Training from logs where one model served almost everything produces a router that just repeats the majority model. Also a 0.6B-forward router adds tens to hundreds of ms per request, so a rules/heuristic stage may be the cheaper first step.
- **Caveats**: Self-reported but candid: status "Experimental"; both corpora are overwhelmingly Claude-Opus-labeled, 19-20 of 28 catalog models have no data, quality label is a constant proxy, latency label is zero. RouterBench models (2023-era) have no overlap with the catalog, scores are via a family/tier bridge. No cost savings measured in production.
