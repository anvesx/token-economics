# 197 — Reasoning models
- **Source**: https://developers.openai.com/api/docs/guides/reasoning (OpenAI, no date)
- **Claim**: OpenAI's reasoning guide says reasoning tokens are billed as output tokens and occupy context, so spend is controlled with reasoning.effort, max_output_tokens, and reasoning persistence settings; effort should be a tuning knob, not the main way to recover quality.
- **Mechanism**: Reasoning models produce internal reasoning tokens before the visible answer. Responses API is recommended over Chat Completions (Chat Completions does not support function calling with GPT-6 Astra or GPT-6.1 Sol). reasoning.effort values: none, minimal, low, medium, high, xhigh, max (model-dependent); lower effort favors speed and fewer tokens, and models reason adaptively. GPT-6 Astra rejects none (HTTP 400); GPT-6.1 Sol rejects none and minimal and defaults to medium; gpt-5.5 defaults to medium. Effort guidance: none for voice, retrieval and classification; low for tool use and chat; medium as default balance; high for hard tasks; xhigh only when evals justify cost; max is the most reasoning. Model picks: gpt-6-astra for most workloads, gpt-5.6-terra for lower cost, gpt-5.6-luna for lowest cost and latency. reasoning.mode "pro" aggregates model work and bills tokens at the model's standard rates, so it costs more. max_output_tokens caps reasoning plus visible output; if hit, the response is incomplete and input and reasoning are paid with no visible output. reasoning.context: auto, current_turn (default before GPT-5.6) or all_turns (default for the GPT-5.6 family, also supported on GPT-6.1 Sol); persisted reasoning is reusable only within the same model family and needs previous_response_id, a conversation, or full replay of output items in original order; current_turn can reduce rendered context in long workflows; changes to history before a reasoning item can make the API drop that reasoning. Stateless mode (store false or ZDR) returns encrypted_content on reasoning items to replay. Function calling requires passing reasoning items back with tool outputs. configuration_update input item (supported on GPT-6 and later, single-agent mode) changes reasoning.effort and text.format mid-conversation while leaving the request-level effort unchanged, which preserves the prompt prefix for caching; it is not compatible with automatic compaction or truncation, and the /responses/compact endpoint rejects histories containing it. Reasoning summaries are opt-in via reasoning.summary (auto, concise or detailed by model); raw reasoning tokens are not exposed; organization verification may be needed. The assistant message `phase` field (commentary or final_answer) should be round-tripped for GPT-5.5 and GPT-5.4 tool-heavy flows to avoid early stopping. Prompting advice: give goal, constraints and an output contract without prescribing every step; define done and how to verify; ask for a short preamble for a faster first visible token.
- **Numbers**: Reasoning ranges from a few hundred to tens of thousands of tokens. OpenAI recommends reserving at least 25,000 tokens for reasoning and outputs when starting. Example usage: input 75, output 1186, reasoning_tokens 1024, total_tokens 1261 (equals 75 + 1186). No prices given.
- **Token-cost implication**: Reasoning tokens are hidden but billed at the output rate and fill context, so set the lowest effort that passes evals, set max_output_tokens with enough headroom (at least 25,000 initially) to avoid paying for reasoning with no visible answer, avoid pro mode unless justified, and keep reasoning items and prior history unchanged across turns so reasoning is reused and the cache prefix survives. Use configuration_update rather than changing request-level effort to keep cache hits. Use current_turn context to shrink context in long workflows.
- **Caveats**: Vendor documentation with no quantified savings or prices. Model names, defaults and support differ by model and are written for the GPT-5.x and GPT-6 families.
