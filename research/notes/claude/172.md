# 172 — Continuous batching
- **Source**: https://huggingface.co/blog/continuous_batching (Hugging Face, 2025-11-25)
- **Claim**: Continuous batching, derived from attention and KV caching, maximizes serving throughput by mixing prefill and decode tokens in one padding-free batch and swapping finished requests out immediately.
- **Mechanism**: KV cache stores per-token K and V so decode is O(n) instead of O(n^2) compute at O(n) memory. Chunked prefill splits long prompts into chunks of at most m tokens using cached KV. Ragged batching concatenates sequences with no batch axis and uses a boolean attention mask to prevent cross-prompt interaction, eliminating padding. Scheduling: fill an m-token budget with all decoding sequences first (1 token each), fill the rest with (chunked) prefill tokens, and replace finished sequences dynamically.
- **Numbers**: KV cache per token = 2 * layers * head_dim * heads values; Llama-2-7B (32 layers, 32 heads, head dim 128) = 8,192 values per token per layer, 16 KB per token per layer in float16 (as stated in text). Dynamic batching with padding needs (n-1)(B-1) padding tokens when inserting an n-token prompt into B decoding prompts; example B=8, n=100 gives 693 padding tokens. No throughput benchmarks.
- **Token-cost implication**: Use a serving engine with continuous batching and chunked prefill (e.g. vLLM-style) rather than static batching; padding and idle slots raise cost per token. KV memory per token bounds batch size, so context length and concurrency trade off.
- **Caveats**: Educational first-principles explainer from Hugging Face, no empirical measurements. A commenter notes the main reason for chunked prefill is preventing long prefills from blocking decodes (SARATHI), not only memory limits.
- **Topic**: serving
