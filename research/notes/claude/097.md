# 097 — XGrammar: Flexible and Efficient Structured Generation Engine for Large Language Models
- **Source**: https://arxiv.org/abs/2411.15100 (arXiv, CMU/NVIDIA/SJTU/UC Berkeley, MLSys 2025, 2024-11)
- **Claim**: A constrained-decoding engine for context-free grammars (JSON, JSON Schema, XML, DSLs) that makes grammar masking nearly free per token, so structured output no longer slows serving.
- **Mechanism**: A byte-level pushdown automaton represents the grammar. For each automaton node, vocabulary tokens are split into context-independent tokens (validity depends only on the stack-top node; precomputed into an adaptive token mask cache keyed by node) and a small set of context-dependent tokens (need the full stack; checked at runtime). The cache stores whichever of accepted or rejected sets is smaller. Context expansion, rule inlining and node merging shrink the context-dependent set. A persistent (tree-structured) execution stack gives fast branching and rollback. Mask computation on CPU is overlapped with GPU model execution. Integrated into MLC-LLM and SGLang.
- **Numbers**: Context-dependent tokens: under 1% (1134 of 128k) for Llama-3.1 with a JSON grammar. Mask cache memory: 160 MB down to 0.46 MB (0.2%). Per-token mask latency (Llama-3.1-8B-Instruct, Ryzen 9 7950X, RTX 4090): under 40 microseconds for JSON Schema and CFG (JSON), under 200 microseconds for XML and Python DSL; up to 3x faster than the best baseline on JSON Schema and over 100x on CFG. Baselines: Outlines v1.0, llama.cpp b3998, lm-format-enforcer v0.10.9. End-to-end on H100 (Llama-3.1-8B, mean input 139 tokens, output 53 tokens): up to 80x output token rate vs existing solutions (vLLM with Outlines v0.6.3, llama.cpp). MLC-LLM time per output token with vs without XGrammar: 6.2 vs 6.3 ms (JSON Schema, batch 1), 9.0 vs 9.2 ms (batch 16), CFG(JSON) 6.3 vs 6.3 and 9.0 vs 9.1 ms. Ablation (mask latency): PDA baseline 65.776 ms, plus node merging 38.280, plus adaptive cache 0.154, plus rule inlining 0.035, plus context expansion 0.018 ms. Syntactic correctness with vs without XGrammar (Llama-3.1 8B): function calling 62% vs 100%, XML code generation 80% vs 100%.
- **Token-cost implication**: Use a fast grammar engine for JSON, function calls and tool outputs; this removes the CPU-side mask overhead that grows with batch size and so avoids paying for slower decode. Guaranteed-valid output removes retries and re-generation of malformed output, which cuts wasted tokens. Choose a serving stack with the grammar engine overlapped on CPU.
- **Caveats**: Self-reported by the authors. Evaluated mostly on Llama-3.1-8B (plus DeepSeek-V2-Lite in one table) with short outputs (53 output tokens) and small datasets (json-mode-eval; synthetic XML and Python sets). The 62% and 80% accuracy rows measure syntactic validity only, not task quality. Large speedups are against the slowest baselines at larger batch sizes; some baseline runs at batch 32 timed out. Figure 10 numbers are garbled in extraction, so only table and prose figures are cited.
