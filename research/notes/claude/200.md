# 200 — Extended thinking tips
- **Source**: https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/extended-thinking-tips (Anthropic, no date). The URL redirects to the "Prompting best practices" reference for current Claude models.
- **Claim**: Anthropic's prompting reference for current Claude models says thinking depth and token spend should be controlled with the effort setting, adaptive thinking and explicit prompt guidance rather than budget_tokens, and gives prompts to curb overthinking, over-verification, excess subagents and early stopping.
- **Mechanism**: Claude 4.6 and later models use adaptive thinking (`thinking: {type: "adaptive"}`) with the `effort` parameter in `output_config`; thinking depth follows effort and query complexity, and easy queries get direct answers. Adaptive thinking is said to beat extended thinking in internal evaluations. Manual `budget_tokens` is deprecated on Opus 4.6 and Sonnet 4.6, and returns a 400 error on 4.7 and later. For a hard ceiling, lower effort or use `max_tokens` with adaptive thinking. Thinking defaults: off when omitted on Opus 4.6 to 4.8 and Sonnet 4.6; on by default on Opus 5, Sonnet 5.5, Sonnet 5, Haiku 5.5; always on for Fable 5.1, Mythos 5.1, Fable 5, Mythos 5 and Opus 5.5. Prompt snippets to reduce thinking: "choose an approach and commit to it", and "Thinking adds latency ... When in doubt, respond directly." Other cost-relevant guidance: put long documents at the top and the query at the end; remove "think" sensitivity on Opus 4.5 when thinking is off; remove self-verification instructions on Opus 5 because they cause over-verification; avoid prefilled responses (400 error from 4.6); steer parallel tool calls to cut round trips; damp subagent spawning; tell the model its context will be compacted so it does not stop early; start fresh context windows with state files (progress.txt, tests.json, git log) instead of compaction in some cases; on Fable 5.1, Opus 5, Sonnet 5.5 and Haiku 5.5 asking the model to write reasoning out in tags may be declined, so use thinking at lower effort if cost or latency matters; on Opus 5, raising or lowering effort does not reliably change visible response length; on Fable 5.1 keep history append-only and pass thinking blocks back unchanged because editing earlier turns invalidates later thinking blocks. Medication-dosing block notes that web search adds latency and search costs.
- **Numbers**: Queries at the end can improve response quality by up to 30 percent in tests (multidocument, long inputs of 20k+ tokens). Examples use max_tokens 16000 and budget_tokens 10000 (older config). Tests example: 200 total, 150 passing, 25 failing, 25 not started. Few-shot: 3 to 5 examples recommended. No prices or token-saving percentages.
- **Token-cost implication**: Control reasoning spend with effort level first, then prompt guidance to commit to an approach and respond directly on easy queries; use max_tokens as the hard cap. Drop legacy verification and "be thorough" prompting when moving to newer models to avoid extra tokens. Batch parallel tool calls to cut turns, limit subagent spawning, and keep conversation history append-only to preserve thinking blocks and cache.
- **Caveats**: Vendor guidance with no quantified savings; model names and behaviours are model-specific and the page says to re-check against your own evals.
