# 106 — DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving
- **Source**: https://arxiv.org/abs/2401.09670 (arXiv, Peking University / StepFun / UC San Diego, 2024-01; v3 June 2024)
- **Claim**: Run prefill and decoding on separate GPUs, sized and parallelized independently, so neither phase interferes with the other's latency. This raises the request rate served per GPU under both time-to-first-token (TTFT) and time-per-output-token (TPOT) limits.
- **Mechanism**: Prefill instances process prompts and send the KV cache to decoding instances. Each phase gets its own GPU count and parallelism (intra-op vs inter-op); prefill is compute-bound and favors intra-op parallelism to cut TTFT, decoding is memory-bandwidth-bound and benefits from batching. A placement algorithm plus a simulator searches the allocation to maximize per-GPU goodput (max request rate with at least 90% SLO attainment), then replicates to reach the target traffic. Placement is bandwidth-aware: prefill and decoding of the same pipeline stage are kept on one machine so the KV transfer uses intra-node NVLink. Chunked prefill with piggybacking is argued to only trade TTFT for TPOT and to need O(N^2) KV cache loads for N chunks.
- **Numbers**: Headline: up to 7.4x more requests or 12.6x tighter SLO vs state-of-the-art, with more than 90% of requests within the latency limits. Motivating example (13B model, A100, input 512, output 64): colocated goodput about 1.6 rps per GPU; prefill alone 5.6 rps, decoding alone 10 rps; with 2 prefill GPUs and 1 decode GPU, 10 rps over 3 GPUs = 3.3 rps per GPU, 2.1x higher. Chatbot (ShareGPT, OPT-13B/66B/175B): 2.0x-4.6x higher rate than vLLM, 1.6x-7.4x vs DeepSpeed-MII, 1.8x-3.2x tighter SLO than vLLM. Code completion (OPT-66B): 5.7x rate and 1.4x tighter SLO vs vLLM. Summarization (OPT-66B, LongBench): 4.3x rate and 12.6x tighter SLO vs vLLM; 1.8x and 2.6x vs DeepSpeed-MII. KV transmission under 0.1% of total latency for OPT-175B; over 95% of requests see under 30 ms delay. Testbed: 4 nodes, 32 A100-80GB GPUs, NVLink in node, 25 Gbps cross-node. 175B placement found: prefill inter-op 3 / intra-op 3, decoding inter-op 3 / intra-op 4. Needing roughly 90 Gbps for a stated transfer rate makes the transfer overhead invisible (text partially read).
- **Token-cost implication**: Cost per query falls when you buy GPUs per phase instead of over-provisioning colocated replicas to hit both TTFT and TPOT. If you run your own serving, evaluate prefill/decode disaggregation (and its network requirements) before scaling out; track goodput per GPU under the SLO, not raw tokens per second.
- **Caveats**: Self-reported by the authors on OPT models (13B, 66B, 175B) with synthetic and benchmark workloads (ShareGPT, HumanEval-style code completion, LongBench), FP16 and fp16 MHA; compared with vLLM and DeepSpeed-MII of that time (2023-2024), not newer chunked-prefill releases. Needs fast GPU interconnect for the KV transfer; the paper says performance would be worse with limited cross-node bandwidth, mitigated only by placement. The simulator assumes known workload arrival patterns. Figure data is garbled in the extraction.
