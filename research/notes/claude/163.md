# 163 — How to Reduce KV Cache Bottlenecks with NVIDIA Dynamo
- **Source**: https://developer.nvidia.com/blog/?p=106133 (NVIDIA, 2025-09-18)
- **Claim**: Offloading KV cache from GPU memory to CPU RAM, SSD or networked storage via Dynamo's KV Block Manager avoids recomputation, raises concurrency and lowers cost per token for long-context, multi-turn serving.
- **Mechanism**: KVBM has three layers: a model-integration layer (TensorRT-LLM, vLLM, SGLang soon), a memory-management layer (tracks block location, customizable offload policy), and a storage/transfer layer using the NIXL library with plugins for CPU, SSD, file systems and cloud. Config for vLLM: `DYN_KVBM_CPU_CACHE_GB` and `DYN_KVBM_DISK_CACHE_GB` env vars plus a `DynamoConnector` kv-transfer-config. Alternative: LMCache via `ENABLE_LMCACHE=1`, `LMCACHE_CHUNK_SIZE=256` (default), `LMCACHE_LOCAL_CPU=True`, `LMCACHE_MAX_LOCAL_CPU_SIZE` (GB); backends CPU RAM, local disk, Redis, GDS, InfiniStore/Mooncake. Metrics via Prometheus/Grafana KVBM dashboard; benchmark with LMCache LMBenchmark synthetic multi-turn chat, baseline by running vLLM without KVBM.
- **Numbers**: Vast: 35 GB/s to a single H100 via GDS plugin; Qwen3-32B with 130K-token prompt on DGX H100, loading precomputed KV from storage reduced TTFT (no figure given). WEKA: read throughput up to 270 GB/s across eight H100 GPUs. Example sizes in the tutorial: 4 GB CPU, 8 GB disk, 20 GB LMCache CPU limit.
- **Token-cost implication**: If you self-host, offload KV cache for long sessions, high concurrency and shared prefixes (system prompts) so evicted prefixes are loaded rather than recomputed; this is the basis for cheaper cached-input-token pricing. Benchmark with and without it on your own multi-turn traffic.
- **Caveats**: Vendor blog; storage-vendor results are throughput tests, not end-to-end cost or latency percentages. TTFT reduction for Vast is stated without a number. Benefits require reuse to outweigh transfer overhead; best on high host-device bandwidth platforms.
