# 113 — GPT Semantic Cache: Reducing LLM Costs and Latency via Semantic Embedding Caching
- **Source**: https://arxiv.org/abs/2411.05276 (arXiv, Sajal Regmi and Chetan Phakami Pun, v3 9 Dec 2024; 2024-11)
- **Claim**: Caching LLM answers keyed by query embedding lets a customer-support style app skip API calls for semantically similar repeat questions. On 500 test queries per category it reports cache hit rates of 61.6% to 68.8%.
- **Mechanism**: Embed each incoming query (OpenAI text-embedding-ada-002, 1536 dims, or a local ONNX model such as all-MiniLM-L6-v2, 384 dims). Search an HNSW approximate-nearest-neighbor index (hnswlib-node) over stored query embeddings by cosine similarity. If the best score is at least 0.8, return the stored response (hit). Otherwise call the LLM API, then store the query, embedding and response in Redis and add the embedding to the index (miss). Cache is partitioned by embedding size and entries have a TTL. The 0.8 threshold was chosen by sweeping 0.6 to 0.9 in steps of 0.05: lower thresholds raised hits but admitted irrelevant matches; higher thresholds cut hits. Hits were validated with GPT-4o Mini, which judged whether the test query and the cached question were semantically similar and the cached answer correct.
- **Numbers**: Dataset: 8,000 question-answer pairs across four categories to prefill the cache; 2,000 test queries (500 per category). Cache hits of 500 and positive hits (Table 1): Python basics 335 (67%) / 310; network technical support 335 (67%) / 326; order and shipping 344 (68.8%) / 331; customer shopping QA 308 (61.6%) / 298. API calls fall to 33%, 33%, 31.2%, 38.4% of the no-cache baseline. Positive-hit rate per hit, computed from Table 1: 92.5%, 97.3%, 96.2%, 96.8%; the text itself states a range of 92.5% to 97.3% but the abstract says "exceeding 97%". Average response time results are shown only as a figure; no values in the text. No dollar figures.
- **Token-cost implication**: For repetitive FAQ-style traffic, put an embedding-similarity cache in front of the LLM and expect roughly one-third to two-thirds of calls to be avoidable. Tune the threshold on your own data and audit false hits, since the paper's own numbers imply 3% to 7.5% of hits were wrong. Count the embedding call and Redis cost against the savings. Do not use it for context-dependent or multi-turn traffic.
- **Caveats**: Small self-run study by the authors on synthetic Q&A categories, with an LLM (GPT-4o Mini) as the sole accuracy judge. Threshold tuned and evaluated on related data. No cost in dollars, no latency numbers in text, no comparison with provider prompt caching. The authors list that the fixed threshold may not generalize, TTL is insufficient for fast-changing data, large indexes add update overhead, and multi-turn context is not handled.
- **Topic**: caching
