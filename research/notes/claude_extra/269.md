# 269 — The components of agent memory
- **Source**: https://www.anthropic.com/research/components-of-agent-memory (Anthropic, 2026-11)
- **Claim**: Anthropic describes how Claude uses memory notes and "dreaming" (offline background passes over transcripts and memory) to correct, reorganize and promote memory, and reports that giving agents a small, well-organized memory (and wikis combined with search) improves results and can reduce tokens.
- **Mechanism**: Claude writes notes to a persisted memory directory during sessions; dreaming runs separate sessions that check notes against transcripts (ground truth), fix errors, build representations such as linked wiki pages, merge duplicates, repoint broken links, and promote notes into a small always-loaded top layer. Steering advice: tell Claude what memory is for, not how to use it; rigid rules (e.g. "record only failures") reduced gains for stronger models, while prompting older models to read memory first and test their theories helped. Claude Code auto memory loads only the first 200 lines or 25 KB of MEMORY.md as an index. Wiki building used 128 sessions of Opus 5 agents coordinating with a shared log; one-agent-per-contract pages that quoted terms verbatim fixed lost facts from agents overwriting a shared table.
- **Numbers**: Stainless corpus ~350,000 files, roughly 420M tokens, 25 questions: wiki-only performance rose from 13% to 48% of graded criteria scaling dreaming from 2 to 128 sessions; search plus wiki rose from 54% to 61% as the wiki grew vs 53% with search alone; search plus wiki saved about 20,000 tokens per question. Merger questions (24): 87% with wiki vs 73% with search alone (on multi-document items). Contract facts in wiki: 41 of 57 (72%) with shared table, 57 of 57 (100%) with one page per contract. Pokemon Red at ~10,000 steps: Sonnet 3.7 wrote 413 memory files across 225 folders and earned one badge; Fable 5 wrote nine files in two folders plus global.md and earned four badges. Sonnet 5 read memory before answering 9 of 10 times vs under half for Sonnet 4.6; prompting Sonnet 4.6 to read memory and test theories "nearly doubled" its CL-Bench score (exact figures only in charts).
- **Token-cost implication**: Keep the injected memory layer small and index-like because every injected token is paid on every session and longer instruction files reduce adherence; store only what cannot be re-read from the environment. Use a wiki together with search rather than either alone, and spend background (dreaming) compute to prune and correct memory instead of letting it bloat. A wiki can grow larger than the source files and abstract nothing.
- **Caveats**: Self-reported by Anthropic on its own models and internal benchmarks (CL-Bench 1.0, Harvey LAB, Pokemon, an internal Stainless corpus with only 25 questions); mostly single runs, with figures given in charts not recoverable from the text. Dreaming itself requires compute whose cost is not quantified.
