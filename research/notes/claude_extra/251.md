# 251 — Reasoning models (OpenAI platform)
- **Source**: https://platform.openai.com/docs/guides/reasoning (OpenAI, no date)
- **Claim**: OpenAI's guide to reasoning models explains the reasoning.effort and reasoning.mode controls, how reasoning tokens are billed and counted, and how to preserve reasoning and prompt-cache prefixes across turns.
- **Mechanism**: reasoning.effort (Responses) / reasoning_effort (Chat Completions) takes model-dependent values from none, minimal, low, medium, high, xhigh, max; lower effort favors speed and lower token usage, and models also reason adaptively (fewer tokens for simple tasks). Recommended use: none for latency-critical tasks (voice, retrieval, classification); low for efficient tool-use/planning/support; medium as default balance; high for hard debugging/planning; xhigh only when evals show a clear benefit; max for the most complex tasks. For GPT-5.6 and GPT-6 models reasoning.mode "pro" aggregates more model work, billed at the selected model's standard token rates; mode and effort are independent. Reasoning tokens are invisible but occupy context and are billed as output tokens; max_output_tokens caps total generated tokens (reasoning plus visible). Hitting the cap returns status incomplete with reason max_output_tokens, possibly before any visible output. reasoning.context (current_turn vs all_turns) controls whether earlier-turn reasoning is rendered into the next sample (GPT-5.6 defaults to all_turns; earlier models to current_turn); persisted reasoning reuses only within the same model family. In stateless mode (store false or ZDR) reasoning items carry encrypted_content to replay. On supported GPT-6 and later models a configuration_update input item changes effort (and text.format) between responses while leaving request-level reasoning.effort unchanged, which preserves the prompt prefix for caching; it must not be combined with automatic compaction or truncation. Reasoning summaries are opt-in via the summary parameter. Prompting advice: give goal, constraints and output contract rather than prescribing steps; treat effort as a tuning knob, not the primary way to recover quality.
- **Numbers**: Models may generate "a few hundred to tens of thousands" of reasoning tokens. OpenAI recommends reserving at least 25,000 tokens for reasoning and output when starting. Example usage object: input_tokens 75, output_tokens 1186 of which reasoning_tokens 1024, total_tokens 1261. gpt-5.5, GPT-5.6, GPT-6.1 Sol, GPT-6 Sol and GPT-6 Luna default to medium effort; GPT-6 Astra rejects effort none with HTTP 400; GPT-6.1 Sol does not support none or minimal. Model suggestions: start with gpt-6-astra, gpt-5.6-terra for lower cost, gpt-5.6-luna for lowest cost and latency. No prices given.
- **Token-cost implication**: Set effort per workload rather than defaulting high, and escalate only where evals show gains. Always set max_output_tokens with headroom so you do not pay for reasoning that yields no visible answer. Change effort mid-conversation with configuration_update rather than editing request-level settings to keep the cache prefix. Use current_turn context to reduce rendered context on long workflows; keep reasoning items in order when replaying history.
- **Caveats**: Vendor documentation; no benchmark or cost-vs-quality figures on this page, and model names reflect this document's catalog. Supported effort values and defaults vary by model, so check each model page.
