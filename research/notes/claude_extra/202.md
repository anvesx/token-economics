# 202 — Prompt Caching 201
- **Source**: https://developers.openai.com/cookbook/examples/prompt_caching_201 (OpenAI, Erika Kettleson, Feb 18, 2026; archived recipe, applies only to models before GPT-5.6)
- **Claim**: Practical guide to maximizing OpenAI prompt-cache hit rate: keep the prefix stable, shape routing with prompt_cache_key, use Responses API, measure cached_tokens, and mind compaction and truncation.
- **Mechanism**: Cache hits need an exact repeated prefix of at least 1024 tokens (hits in 128-token increments) that lands on the same machine. The cache stores key/value attention tensors for the prefix, so only new suffix tokens go through prefill. Requests route by a hash of the first ~256 tokens; prompt_cache_key is combined with that hash to increase stickiness. Each prefix + key combination handles roughly 15 requests per minute per engine; overflow goes to other machines, each a one-time miss, so pick key granularity (per user, per conversation, or hashed user id mod N buckets) to stay under ~15 RPM. Put instructions, tools and schemas first, volatile content last; keep tool order and schema keys fixed; restrict tools per turn with the allowed_tools tool_choice option instead of changing the tools array; move timestamps to metadata. Responses API persists reasoning tokens via previous_response_id or encrypted reasoning items, unlike Chat Completions. Flex processing (service_tier="flex") gives the same 50% discount as Batch, plus RPM control, extended caching and prompt_cache_key. Extended retention (prompt_cache_retention "24h") offloads KV tensors to GPU-local storage; for gpt-5.5, gpt-5.5-pro and later the default is 24h and in_memory is unsupported. Realtime API: truncation retention_ratio (e.g. 0.7) drops older context in one large event rather than per turn, keeping the prefix stable.
- **Numbers**: Latency up to 80% lower TTFT and input cost up to 90% lower (vendor claim). Author's 2300-run test: 1024-token prompts 7% faster cached; 150k+ tokens 67% faster TTFT. Prices per 1M input / cached input: gpt-4o $2.50 / $1.25 (50%); gpt-4.1 $2.00 / $0.50 (75%); gpt-5-nano $0.05 / $0.005 (90%); gpt-5.2 $1.75 / $0.175 (90%); gpt-realtime audio $32.00 / $0.40 (98.75%). Lengthening a 900-token prompt to 1100 tokens: 50% cache rate saves 33%, 70% saves 55%. prompt_cache_key raised one coding customer's hit rate from 60% to 87%. Flex vs Batch, 10,000 identical requests: +8.5% cache hit rate, 23% lower input token cost. Responses API: 40-80% better cache utilization than Chat Completions (internal benchmark). Realtime: 32k context with 4,096 max output leaves 28,224 tokens of context.
- **Token-cost implication**: Treat the prefix as a performance surface: static content first, no timestamps or reordered tools, key by user or conversation sized under ~15 RPM, log cached_tokens every request, use Responses API for reasoning models, and choose compaction frequency with evals because compaction breaks the cache. Consider Flex over Batch for cache-friendly async work, especially for pre-GPT-5 models that Batch does not cache.
- **Caveats**: Author is OpenAI staff, self-reported; Flex test is one 10,000-request experiment; cache is best-effort; archived and not applicable to GPT-5.6 and later (see the newer Prompt Caching guide).
