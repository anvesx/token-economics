# 116 — Long Context vs. RAG for LLMs: An Evaluation and Revisits
- **Source**: https://arxiv.org/abs/2501.01880 (arXiv; Xinze Li, Yixin Cao, Yubo Ma, Aixin Sun; NTU S-Lab and Fudan University; v1 27 Dec 2024; 2025-01)
- **Claim**: On a filtered, expanded set of 12 QA datasets, feeding the full context to a long-context (LC) LLM beats RAG overall (56.3% vs 49.0% correct by strict exact match). Summarization-based retrieval (RAPTOR) comes closest, and RAG wins on dialogue and general yes/no questions.
- **Mechanism**: Three phases. (1) Filter out questions that GPT-4o answers correctly without any context (exact match), so scores depend on external context. (2) Compare five retrievers on a small sample set (1,000+ questions) and pick the best: BM25, Contriever, OpenAI text-embedding-3-small (chunk-based); Llama-Index Tree Index and Sentence Window (index-based); RAPTOR (summarization tree, collapsed-tree traversal over all levels, top-k nodes up to a token limit). (3) Run LC (whole context, truncated from the back if it exceeds the window) vs RAG with RAPTOR on the expanded set, using the same generator (GPT-4o), same prompt ("From the context: [context], answer the questions briefly with no explanation"). Scoring is strict EM, plus a loose mode where the method with the higher token-set F1 "answers better". The set was expanded about 10x using the original sources and LongBench-style distractor passages.
- **Numbers**: 12 datasets; 19,188 questions after expansion; Table 3 reports 13,628 kept (71%) after filtering (the text says 13,651, so the two disagree). Retriever test (sample set, Table 5; correct count and %): BM25 319 (20.4), Contriever 315 (20.1), text-emb-3-small 338 (21.6), Tree Index 470 (30.1), Window Parsing 555 (35.5), RAPTOR 602 (38.5). Overall on 13,628 questions (Table 4): LC correct 7,676 (56.3%), RAG correct 6,683 (49.0%); LC only correct 2,287, RAG only correct 1,294 (almost 10% of questions); loose mode LC better 3,433, RAG better 1,843. Generator swap (Table 6, RAPTOR): GPT-4o 602 (38.5%) vs GPT-4-Turbo 589 (37.7%). By source, LC wins on Wikipedia (Fig 3 only-correct counts LC 873 vs RAG 348) and story; RAG wins on dialogue (RAG 44 vs LC 31 in Fig 4/5 labels; the figure text is garbled). By question type, LC wins "Who/Where/Which"; RAG wins "Other" (yes/no). Survey claims from prior work: top 5 to 10 chunks work well, more than 20 chunks hurts (Xu et al.); RAG for closed models improves up to 100K tokens, open models peak at 16K to 32K (Leng et al.); Self-ROUTE finds LC better but RAG cheaper. No dollar or token-cost numbers.
- **Token-cost implication**: For one coherent document or book, sending the full context is more accurate, but you pay for every input token; RAG gives a much smaller prompt at lower accuracy. For fragmented sources such as chat or dialogue logs, and for open or yes/no questions, retrieval is the cheaper and equal or better choice. If you use RAG, prefer hierarchical summary retrieval or sentence-window over plain chunk search, keep the chunk count low, and consider routing per query type. Pair LC with prompt caching if you re-send the same long context.
- **Caveats**: Academic study by the authors, one generator family (GPT-4o, with a small GPT-4-Turbo check), strict EM scoring that penalizes long answers. Many Wikipedia contexts were synthetically padded with noise, which the authors say biases against RAG. It does not measure cost, latency or tokens; the cost argument is not tested. Text only; newer models and retrievers may change the outcome. Datasets were filtered using GPT-4o itself.
