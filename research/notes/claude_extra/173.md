# 173 — Prompt caching
- **Source**: https://docs.mistral.ai/inference/conversations/advanced/prompt-caching (Mistral AI, date not stated)
- **Claim**: Mistral's API caches shared prompt prefixes and bills cached prompt tokens at 10% of the standard input token price.
- **Mechanism**: Set the same prompt_cache_key (stable identifier such as conversation, session or workflow ID; no secrets) on requests likely to share a prefix and keep the prefix identical and append-only across turns. The key raises the chance of a hit but does not guarantee one. Cached tokens appear in usage.prompt_tokens_details.cached_tokens; uncached billable input = prompt_tokens - cached_tokens. Cache blocks contain 64 tokens, so prompts under 64 tokens get no hits. Best for multi-turn chat, repeated system prompts, fill-in-the-middle, agent turns; less useful for short or unrelated prompts or ones changing the start of the prompt.
- **Numbers**: Cached tokens billed at 10% of standard input price (a 90% discount). Worked example (mistral-large-latest): prompt_tokens 1013, cached_tokens 1008, completion_tokens 30 -> 5 uncached input tokens at standard price, 1008 cached at 10%, 30 output tokens at output price. Block size 64 tokens (note: the example's 1008 is not a multiple of 64, contradicting the stated rule). No explicit minimum TTL, write charge or dollar price stated.
- **Token-cost implication**: Put stable content first, keep history append-only, set a per-session prompt_cache_key, and check cached_tokens in responses; for long repeated prefixes the input cost falls to 10% on the cached part. Track via Admin Panel > Usage per model.
- **Caveats**: Vendor documentation, no measured hit rates; hits not guaranteed. Latency reduction is claimed qualitatively ("can reduce"). Internal inconsistency between the 64-token multiple statement and the 1008 example.
- **Topic**: caching
