# 182 — Context Caching
- **Source**: https://api-docs.deepseek.com/guides/kv_cache/ (DeepSeek, date not stated)
- **Claim**: DeepSeek API enables on-disk context caching by default for all users with no code changes; a request hits the cache only if it fully matches a persisted prefix unit.
- **Mechanism**: Every request builds a disk cache. Because of Sliding Window Attention, each cached prefix is an independent complete unit and a later request must fully match one to hit. Prefix units are persisted at: (1) request boundaries, the end of user input and the end of model output; (2) common-prefix detection, when requests share a prefix the system persists it; (3) fixed token intervals for long inputs or outputs. Example: requests A+B then A+C miss, but the system then persists A so a third request A+D hits A. Usage fields prompt_cache_hit_tokens and prompt_cache_miss_tokens report hits. Matching is on prefix only; outputs still vary with temperature.
- **Numbers**: none (no prices on this page; see the pricing page). Cache construction takes seconds; unused caches are cleared usually within a few hours to a few days. Not a 100% hit guarantee ("best-effort").
- **Token-cost implication**: Put the stable material (system prompt, long document) first and the question last so repeated requests share a full prefix unit; a cache needs one or two prior requests before a shared prefix gets persisted, so first calls will miss. Read prompt_cache_hit_tokens to verify.
- **Caveats**: Vendor documentation; no measured hit rates or latency figures. Hit requires exact full-unit match, not arbitrary partial overlap.
- **Topic**: caching
