# 009 — FLARE: Fine-Grained Length-Aware Routing for Resource-Efficient Heterogeneous LLM Serving
- **Source**: https://aclanthology.org/2026.acl-long.1018 (ACL 2026, Sun Yat-sen University, 2026-07)
- **Claim**: FLARE is a length-centric, resource-aware multi-LLM router that estimates per-query output length to predict latency and cost, then solves routing as a multi-objective optimization under an accuracy constraint, cutting latency and cost substantially with modest accuracy loss.
- **Mechanism**: Offline profiling collects per-(query,model) correctness, generated length, end-to-end latency, and cost. Features = all-MiniLM-L6-v2 384-d query embedding + query attributes (prompt length, dataset type, difficulty bucket from cross-LLM correctness rate) + model descriptors (param size, release year, knowledge coverage, serving mode). Two XGBoost predictors (max_depth=8, lr=0.05, subsample=0.8): accuracy predictor facc (binary) and output-length predictor flen. Latency modeled per-LLM linearly T̂=k·L̂+b (fit by OLS); cost = input_price·ℓ_in + output_price·L̂. Routing: filter candidates with p̂≥τ (prefer small LLMs, fall back to large), then minimize weighted objective P=α·T+β·C (FLARE-Efficient) or P=α·T+β·C+ω·error (FLARE-Balance), or maximize accuracy (FLARE-Acc). Pareto frontier / IGD measures closeness to ideal. Cold-start: bootstrap (k,b) from a few latency-length traces for new LLMs, refine online.
- **Numbers**: Reduces mean latency by up to 68% and cost by up to 75% while maintaining sufficient accuracy. vs Acc-Best, FLARE-Acc cuts latency up to 59% and cost up to 69% at similar accuracy. FLARE-Efficient cuts latency 26–68% and cost 44–75% vs RouterBench/TensorOpera, at 5–20% accuracy sacrifice. Output length↔latency: Pearson r=0.9605, R²=0.9225 (DeepSeek-R1 fit y=10.48x+292.3). Length-prediction R²: XGBoost 0.6122 (MAE 101.2) vs BERT+MLP 0.5649. Predicting latency from predicted length R²=0.616 (0.5791 overall). Accuracy predictor: XGBoost F1=0.8856, AUC=0.9351. Cold start converges ~200 requests (batches of 25). Routing overhead 18.12±0.02 ms/query vs ~1500 ms fastest-model latency. Pricing ($/1M in→out): deepSeek-R1-671B 0.56→2.19, gemma3:27b 0.04→0.15, llama3:8b 0.03→0.06, mathstral:7b 0.15→0.15, phi4 0.06→0.14, qwen2.5:7b 0.04→0.10, small <7B models ~0.01→0.02. Robustness: even at length-predictor R²=−1, FLARE-Efficient still cuts latency/cost/IGD 68.9%/78.6%/76.8% vs always-DeepSeek-R1. Hyperparams: FLARE-Efficient α=0.55,β=0.45,τ=0.5; FLARE-Balance α=0.4,β=0.25,ω=0.35,τ=0.5. Models on Apple M4 (7B) and RTX 3060 (<7B).
- **Token-cost implication**: Predict output length first (cheap XGBoost on query+model features) because length ~linearly drives both latency and dollar cost; filter by an accuracy threshold then minimize a tunable latency/cost objective, and expose preset modes (accuracy-first / efficiency-first / balanced) so deployments pick an operating point without expensive candidate inference.
- **Caveats**: Self-reported by authors. Length/latency prediction is noisy and affected by runtime contention, KV-cache, decoding config; accuracy modeled as binary (no content quality). Benchmarks use short standard queries (GSM8K, ARC-Easy, MBPP, MMLU, MuSR + OOD CommonsenseQA, MATH), not real production traffic. Latency depends on specific hardware tiers used; users cannot finely tune (α,β) via presets.
- **Topic**: routing
