# 125 — How to Build a Generative AI Cost and Usage Tracker
- **Source**: https://www.finops.org/wg/how-to-build-a-generative-ai-cost-and-usage-tracker (FinOps Foundation, none)
- **Claim**: A practitioner guide for tracking and attributing generative-AI inference costs using tokens as the primary unit, covering three tracking methods, centralized vs decentralized architectures, a database schema, and a method for attributing shared Provisioned Throughput Unit (PTU) costs.
- **Mechanism**: Tokens split into input (prompts, billed cheaper) and generated (responses, billed higher). Three tracking approaches by increasing accuracy/effort: (1) count requests per API key and bill per call (inaccurate — "hello" costs same as 1.2M-token input); (2) token estimation via libraries (only estimates unless tokenization published), recorded to a SQL/NoSQL DB and rolled up per key/use case at billing period; (3) actual input/output token counts from model responses into a DB. Provided schema: tables request_keys, model_information (input/output price, effective date), api_versions, token_tracking (input/output counts, model_id, computed total_cost). Centralized hub-and-spoke: route all AI calls through a proxy with per-use-case API keys and per-call token attribution. Decentralized: provide a common SDK/IaC module with built-in tagging/load-balancing, or separate billing entities per workload. PTU (reserved capacity, fixed cost, no per-token billing): compute an effective per-token rate and attribute by each use case's token consumption × utilization-adjusted rate: Spend = PTU_Rate × (2 − Utilization Rate) × Mtoken count; combine with timestamps for fair showback/chargeback.
- **Numbers**: Cutting-edge models cited at USD 10–20 per Mtoken generated (as of writing). 1,000 × 100-word emails ≈ 100,000 tokens (word count underestimates true token count). PTU worked example: AWS Provisioned Throughput of Claude 2.0 = $29,462.40/month; assume 1 PTU = 2,500 input + 250 output tokens/min → ~5 Gtoken input + ~0.6 Gtoken output/month; at standard $8/Mtoken input + $24/Mtoken output that is $41,472 + $15,552 = $57,024, giving effective PTU rate 29,462.40/57,024 = 0.516 (→ $4.133/Mtoken in, $12.40/Mtoken out). At 50% utilization, 1 Gtoken use case (700M in/300M out): PTU spend $4,339 + $5,580 = $9,919 vs $12,800 non-PTU. Three-use-case example (75% util): A $6,713, B $774, C $2,322.
- **Token-cost implication**: Track actual input/output token counts (not request counts) in a dedicated DB keyed per use case; enforce per-use-case API keys through a centralized hub or a common tagging SDK; for shared PTUs, derive a utilization-adjusted effective per-token rate and attribute by consumption to enable fair chargeback.
- **Caveats**: Vendor/community guidance (FinOps Foundation working-group whitepaper), not an empirical study. Token estimates are inexact unless the model's tokenization is published. Do not store raw prompts/outputs long-term (sensitive-data risk). PTU attribution relies on assumptions (e.g., 100%-utilization effective rate); throughput/pricing transparency is lacking across providers so estimates are "best option." Covers inference costs only, not storage/backup/load-balancing. Page is undated; references a "State of Tokenomics: September 2026" report. "a single PTU" is not comparable across providers.
- **Topic**: observability
