# 224 — Prompt Caching: Cut the Cost of Long Chats with the Grok API
- **Source**: https://docs.x.ai/cookbook/examples/prompt-caching (xAI, 2026-11)
- **Claim**: Prompt caching reads a repeated prompt prefix at a quarter of the input price, but putting a changing value (the current time) at the top of the system prompt breaks the cache and makes the same 30-message chat cost 2.2–2.9× as much. Compaction often costs more than it saves for short chats.
- **Mechanism**: A worked TypeScript example plays the same 30 messages in three chats against grok-4.7 with a ~2,100-token handbook resent every prompt. Caching works only when a prompt starts the same way as the last one. Chat 1 puts the changing time at the top of the latest user message (part of the new content anyway) → high cache reuse. Chat 2 puts it at the top of the system prompt → that one line makes the entire prompt new every turn → cache miss on everything but a shared preamble. Chat 3 is like Chat 1 but compacts via responses.compact() once turns since last compaction exceed COMPACT_AFTER (1,500 tokens). prompt_cache_key = "chat:"+id routes each turn to the server holding the cache. response.toInput() carries Grok's encrypted reasoning items forward so the cache covers Grok's earlier answers too. Compaction item must come first (API drops anything before it), so the system prompt+handbook goes right after it to survive verbatim. Pricing computed from token counts: $2.00/MTok input, $0.50/MTok cached, $6.00/MTok output. Caching works in 128-token blocks (every cached count is a multiple of 128; last partial block is always new).
- **Numbers**: One run (30 messages, 3 chats): total 56¢ at list price, 27¢ of it the time-on-top chat; took 3m13s. Per-chat: Time-in-message $0.117, 87% input from cache, median TTFT 0.6s, 0 compactions; Time-on-top $0.270, 3% from cache, 0.7s, 0; With-compaction $0.167, 86% from cache, 0.7s, 3 compactions. Cached price = 1/4 of input ($0.50 vs $2.00/MTok). Time-on-top read only 128 tokens/turn from cache; cost/turn rose 0.6¢→1.2¢ as chat grew 2,400→5,900 tokens vs chat 1's ~0.2–0.5¢. Time-on-top cost 2.3× chat 1 this run, 2.2–2.9× across runs. 3 compactions cost 1.4/1.7/3.3¢ and took 19/29/53s; wrote 600–1,800-token summaries plus up to 2,600 reasoning tokens; removed only 600–900 tokens; turn after each read only 128 cached tokens (~3× a normal turn). With caching each 10,000 tokens a compaction removes saves ~0.5¢/turn. Summaries ranged 15–2,350 tokens in tests; a 15-token one forgot the user's suit number. Without prompt_cache_key the API still cached 64%–95% of input. TTFT up to 80s when API busy, cached or not.
- **Token-cost implication**: Never put volatile values (timestamps, request IDs, random nonces) at the top of the system prompt — pin them to the end of the latest user message so the shared prefix stays cacheable; this alone is a 2–3× cost swing on long chats. Carry encrypted reasoning forward with toInput() so cache coverage extends past the model's prior answers. Only compact when turns are many times the size of a summary or to stay within context — for short chats compaction costs more than it saves and the next turn misses the cache. Expect caching in 128-token blocks.
- **Caveats**: Vendor cookbook; figures are self-reported from the author's own runs and vary run-to-run (2.2–2.9×, 64–95%). Single model (grok-4.7), small synthetic handbook/chat, low reasoning effort. Compaction economics depend on COMPACT_AFTER tuning (set deliberately low here). TTFT measurements confounded by API load and rate-limit retries.
