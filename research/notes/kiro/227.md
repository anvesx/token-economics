# 227 — Provider routing (OpenRouter)
- **Source**: https://openrouter.ai/docs/provider-routing (OpenRouter, 2025-11)
- **Claim**: OpenRouter routes each request to the best provider for a model based on measured effective price, throughput, latency, and reliability, and exposes a `provider` object so callers can override routing to optimize for price, throughput, latency, data policy, quantization, or specific endpoints.
- **Mechanism**: Default routing scores providers from recent production traffic on effective price (reflecting real cache hit rate and the typical input/output token mix), throughput (output tokens/sec), time to first token, 429 rate, reliability, and tool-call quality. Providers near the best share most traffic; each request picks one at random weighted by shares, with far-behind providers kept at a small share for re-discovery. Providers with far-worse errors/429s get zero traffic until recovery; retries re-pick from remaining providers; follow-up requests stay on the same provider while its prompt cache is warm. Override fields in the `provider` object: `order` (ordered provider slugs), `allow_fallbacks`, `require_parameters`, `data_collection` (allow/deny), `zdr`, `enforce_distillable_text`, `only`, `ignore`, `quantizations`, `sort` ("price"/"throughput"/"latency", or object with `by`+`partition`), `preferred_min_throughput`, `preferred_max_latency` (number or percentile object p50/p75/p90/p99 over a rolling 5-minute window), and `max_price`. Shortcuts: `:nitro` (sort by throughput + priority-tier endpoints), `:floor` (sort by price + flex-tier endpoints). `partition: "none"` sorts endpoints globally across fallback models instead of grouping by model. Endpoint slugs have shape `provider[/variant][/region][/tier]`; base slug matches all regions/variants.
- **Numbers**: Percentile window: rolling 5 minutes; percentiles p50/p75/p90/p99. `session_id` / slug limits not covered here. Example thresholds used in docs: `preferred_min_throughput p90: 50` tokens/sec; `preferred_max_latency` p50:1s, p90:3s, p99:5s; `preferred_min_throughput` p50:100, p90:50 tokens/sec. `max_price` example: {"prompt": 1, "completion": 2} = <= $1/M prompt tokens and <= $2/M completion tokens. Quantization levels: int4, int8, fp4/mxfp4/nvfp4, fp6, fp8/mxfp8, fp16, bf16, fp32. Anthropic beta headers: interleaved-thinking-2025-05-14, structured-outputs-2025-11-13.
- **Token-cost implication**: To minimize spend, set `sort: "price"` or `:floor`, optionally with `max_price` and a performance floor (`preferred_min_throughput`/`preferred_max_latency`) so you get the cheapest provider that still meets a latency/throughput SLA. Use `partition: "none"` with price sort across a fallback model list to find the cheapest capable model and to maximize BYOK key usage. `max_price` (unlike the soft `preferred_*` fields) will fail the request rather than overpay. Note default routing uses *effective* price including cache-hit rate, so keeping a conversation on one provider (sticky) preserves cache savings.
- **Caveats**: Vendor documentation (OpenRouter self-published), no independent benchmark. `preferred_*` fields are soft preferences (deprioritize, not exclude) and never guarantee a performance level; only `max_price` can block a request. Metadata/pricing are point-in-time and routing reacts within minutes. Does not quantify actual savings.
