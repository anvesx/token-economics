# 257 — Prompt caching (Fireworks)
- **Source**: https://docs.fireworks.ai/guides/prompt-caching (Fireworks, 2026-11)
- **Claim**: Fireworks prompt caching reuses a common prompt prefix across requests to respond faster and cheaper; it is on by default for all models/deployments and can cut time-to-first-token (TTFT) by as much as 80%, with cached serverless tokens billed at a discount.
- **Mechanism**: Fireworks finds the longest prefix of the request already in cache and reuses it, processing only the remainder; the full prompt is then stored for future reuse. Caching requires exact prefix matches, so static content (system prompt, instructions, examples, tools for function calling) goes first and variable/user-specific content goes last — a single-token difference (e.g. a timestamp at the top) invalidates the whole chain. Caching is replica-local: on serverless or multi-replica deployments, pass a stable per-user/per-session id in the `user` field or `x-session-affinity` header to route prefix-sharing prompts to the same replica. Cache can be reset/isolated via a new session key, `x-prompt-cache-isolation-key` header / `prompt_cache_isolation_key` field, or `reset_prompt_cache` (all/none/new_session). Caching does not change outputs (each generation sampled independently). For gradual traffic migration, use deterministic user-id hashing (MD5 → ratio) rather than random sampling to preserve cache hit rates. Monitoring via `fireworks-prompt-tokens` / `fireworks-cached-prompt-tokens` headers and the usage dashboard.
- **Numbers**: TTFT reduced by as much as 80%. Serverless cached prompt tokens discounted by a default 50% (varies by model — check Model Library). Dedicated-deployment cached tokens are "close to free" (affect context length but need no extra processing). Cached prompts stay in cache at least several minutes, up to several hours depending on model/load/config; oldest evicted first.
- **Token-cost implication**: Structure prompts static-prefix-first / dynamic-last and never put timestamps or dynamic content at the top; round timestamps to larger intervals, inject time only for time-sensitive queries, or move time into the user message. Always pass a stable session/user id to keep prefix-sharing traffic on one replica so the 50% cached discount is actually realized. Use consistent (hash-based) routing, not random, when shifting traffic between deployments.
- **Caveats**: Vendor doc, self-reported; "as much as 80%" TTFT and "close to free" dedicated caching are best-case claims with no independent measurement. Cached discount default 50% but model-specific. Caching only helps on exact-prefix matches and only within one replica. Serverless keeps per-account caches (privacy); a minor timing-attack risk exists, mitigated by the isolation key.
