# 045 — RouterEval: A Comprehensive Benchmark for Routing LLMs to Explore Model-level Scaling Up in LLMs

- **Source**: https://arxiv.org/abs/2503.10657 (arXiv / Sun Yat-sen University, 2025-03)
- **Claim**: Routing LLMs (a router picks the best LLM per input from a candidate pool) exhibits a "model-level scaling up" phenomenon — a capable router improves performance rapidly as the candidate pool grows, surpassing the best single model and many strong LLMs even when candidates are weak. RouterEval is a benchmark (200M+ performance records, 8,500+ LLMs, 12 evaluations) to drive router research.
- **Mechanism**: For each input, a router (an m-way classifier over candidate LLMs) maps the input embedding to a one-hot selection vector marking the LLM(s) that would answer correctly (within 95% of optimal for continuous metrics). Training data = (input embedding, selection vector) pairs plus optional external data. To study the scaling phenomenon, they build an oracle router r_o (always picks a correct LLM) and a tunable router r_o(p) that follows the oracle with probability p and samples uniformly otherwise (p→0 = random, p→1 = oracle). Candidate subsets are sampled 100× per size m. Three candidate-difficulty groups ("all-strong," "all-weak," "strong-to-weak") are constructed by sorting LLMs by individual performance. Metrics: original performance μ_o, reference value V_R (vs a strong LLM like GPT-4), best-single-model value V_B, and classification-bias entropy E_p (low E_p = router collapses to one LLM = overfitting/bias).
- **Numbers**: >8,500 LLMs (8,576 total), >200,000,000 performance records, 12 benchmarks (ARC, HellaSwag, MMLU, TruthfulQA, Winogrande, GSM8k, IFEval, BBH, GPQA, MUSR, MATH Lvl 5, MMLU-PRO). Easy difficulty m∈{3,5}, hard m∈{10,100,1000}; performance grows fastest for 2≤m≤10, and even 3–10 candidates can beat the strong reference model. Scaling requires router capability p≥0.5. Example: MMLU, m=10, "all-weak" group each individual <0.3 accuracy but oracle reaches 0.95. At least 10^30 routers achieve oracle performance per candidate group (learnability). Per-benchmark LLM counts ~1800–5000; train/val/test split 8:1:1. Most LLMs are 7B open-source, performance filtered to 0.1–0.9. Existing router methods (LinearR, MLPR, C-RoBERTa, MLC, PRknn) mostly give V_R ≤ 1 and V_B ≤ 1 (lag best single model and reference); no single router wins across benchmarks; some suffer classification bias (E_p→0). Reference LLM performances e.g. MMLU 0.864 (GPT-4), GPQA 0.397, MATH Lvl 5 0.400.
- **Token-cost implication**: Routing is a cheap, inference-only way to "scale up" by orchestrating a pool of mostly small/weak open-source models — a well-built router over just 3–10 candidates can beat a strong commercial LLM, which is cost-effective for resource-limited users. But today's routers underperform their potential, so investment should go into better routers (using the released 200M records for data augmentation, few-shot, recommender-system/debiasing techniques) before chasing cost/hallucination objectives.
- **Numbers caveat on cost**: The paper deliberately optimizes only for performance, not computational cost or hallucination (defers multi-objective routing). Large pools raise deployment challenges; cost-effectiveness is highest at 3–10 candidates.
- **Caveats**: Self-reported (SYSU). Oracle/r_o(p) results are upper-bound simulations, not achievable routers; the scaling phenomenon is demonstrated with idealized routers. Real router methods still have "significant room for improvement." Benchmark data is static performance records; most real routing data is private/non-open-source, and more data is the key bottleneck. Does not yet consider cost, latency, or hallucination objectives.
- **Topic**: routing
