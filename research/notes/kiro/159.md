# 159 — Capacity and Performance (Amazon Bedrock)
- **Source**: https://docs.aws.amazon.com/bedrock/latest/userguide/capacity-limits-cost-optimization.html (Amazon Web Services, n.d.)
- **Claim**: Amazon Bedrock offers multiple capacity options — on-demand tiers (Flex, Standard, Priority), Reserved tier, Batch, and Cross-Region Inference — each trading cost against throughput, latency, and availability guarantees.
- **Mechanism**: On-demand tiers differ by cost and throughput: Flex = lowest cost per token, best-effort, no SLA, high throttling; Standard = balanced, standard SLA; Priority = highest cost, premium throughput, enhanced SLA, low throttling. Reserved tier buys model units for guaranteed capacity on 1- or 3-month commitments. Batch submits async jobs (prioritized below on-demand) for bulk inference. Cross-Region Inference routes requests across regions in an inference profile, using on-demand pricing. Decision framework maps scenario→tier; optimization advice: start Standard, downgrade to Flex for dev/test, upgrade to Priority only when throttling hits users, move to Reserved when consistent load exceeds ~40% of on-demand cost, monitor CloudWatch throttle metrics.
- **Numbers**: Batch = 50% cost savings vs on-demand; batch job timeout 24h default, configurable up to 168h. Reserved/steady high-volume = 30-50% savings with commitment. RPM/TPM by tier: Flex 10-100 RPM / 5K-50K TPM (high throttling); Standard 100-500 RPM / 50K-150K TPM (medium); Priority 500-1000+ RPM / 150K-300K+ TPM (low). Reserved minimum commitment 1 model unit. Transition to Reserved suggested when consistent load exceeds 40% of on-demand costs.
- **Token-cost implication**: Match workload to tier — use Batch (50% off) for non-urgent bulk jobs, Flex for dev/test, Reserved for steady high volume (30-50% off), and only pay Priority when throttling actually degrades UX; consider global Cross-Region profiles to lower token cost for some models.
- **Caveats**: Vendor documentation, no absolute per-token prices (points to Bedrock pricing page). Actual RPM/TPM limits are model-specific and soft (increasable via quota requests); savings figures are ranges. Batch completion is not guaranteed and lacks tool-calling in some invocation types (per related doc). Batch not supported for provisioned models.
