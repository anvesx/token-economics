# 011 — Arch-Router: Aligning LLM Routing with Human Preferences
- **Source**: https://arxiv.org/abs/2506.16655 (Katanemo Labs, 2025-06)
- **Claim**: Arch-Router is a compact 1.5B generative router that maps queries to user-defined Domain-Action routing policies (rather than optimizing benchmark quality scores), letting users encode subjective preferences and swap models without retraining; it beats top proprietary LLMs at policy matching.
- **Mechanism**: Preference-aligned routing decouples route selection from model assignment. Users define route policies C={(name, natural-language description)} under a two-level Domain-Action taxonomy (Domain = topic e.g. legal/finance; Action = operation e.g. summarization/code generation). A mapping T associates each policy with a preferred LLM; models can be added/removed/swapped by editing T alone. Arch-Router (F) is a generative LLM: given a structured prompt containing the full policy set C and the conversation, it generates the identifier of the best-matching policy (or "other" for irrelevant). Because policies are in the prompt, new routes work at inference with no retraining. Trained via SFT (Llama-Factory, full-param, bfloat16, AdamW, ≤4 epochs, 1 A100) on 43K samples (90/10 split) from a two-phase data pipeline: Phase 1 generates clean labeled multi-turn conversations from verified policies (LLM generates + verifies); Phase 2 augments with irrelevance injection, policy modification, and scenario mixing. Base model Qwen2.5-1.5B.
- **Numbers**: Arch-Router = 1.5B params. Overall routing score 93.17%, beating every other candidate on average by 7.71%. Span-level 94.98%, full-conversation 88.48%. fQfA (action match) 98.11. vs strongest proprietary Claude-sonnet-3.7 (92.79% overall). Latency: Arch-Router 51±12 ms vs Claude-sonnet-3.7 1450±385 ms (>28× faster); other commercial: GPT-4o 836±239 ms, GPT-4o-mini 737±164, Claude-haiku-3.5 1249±352, Gemini-2.0-flash 581±101, Gemini-2.0-flash-lite 510±82. Trained on 43,442 samples. Evaluated on CLINC-150, MANtIS, SGD, LMSYS-1M. Latency benchmarked on 2,000 prompts (commercial via OpenRouter API; Arch-Router self-hosted on AWS L40S). Coding case study: Arch-Router routed 8/8 turns correctly vs RouteLLM mis-routing 3 context-dependent turns.
- **Token-cost implication**: For multi-model production systems where "best" is subjective, use a small (1.5B) generative router that reads route descriptions from the prompt—it adds microsecond-to-~50ms overhead, is far cheaper/faster than using a big LLM as judge/router, and lets you add or swap models by editing a mapping table with zero retraining.
- **Caveats**: Self-reported by authors (Katanemo, who release the model). Commercial-model latencies are OpenRouter snapshots subject to change (server load/network). Accuracy = policy-matching accuracy against LLM-generated-then-verified ground truth, not end-task quality. Routing quality bounded by precision of the policy set (ambiguous/overlapping descriptions degrade it) and by the user's model-to-policy assignment. No performance/cost optimization of the underlying models.
