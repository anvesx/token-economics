# 185 — Reliable LLM Inference at Scale
- **Source**: https://www.databricks.com/blog/reliable-llm-inference-scale (Databricks, 2026-06)
- **Claim**: Databricks' multi-tenant inference platform uses a "model units" abstraction (a VM-like capacity primitive) to allocate, route, and autoscale GPU per customer; cost-aware load balancing and autoscaling on model units saved over 80% in GPU cost vs static provisioning, and profiling fixed a multimodal bottleneck for 3x throughput.
- **Mechanism**: "Model units" estimate per-request cost via a multi-dimensional function of input/output token distribution with coefficients α, β, γ determined by automated benchmarking per model per hardware type (prefill and decode have different throughput, so long-output requests cost more than long-input). A router (Axon) and autoscaler both consume server load measured in model units. Routing uses Dicer (Databricks' auto-sharder) with load-aware, stateful/sticky sessions so a workload hits a subset of servers — improving cache hit rates (important for coding agents) and limiting blast radius — instead of request-count P2C heuristics. Autoscaler scales on the model-unit utilization ratio vs the engine's max. Reliability: periodic black-box health checks (minimal end-to-end requests) trigger a Kubernetes liveness-probe restart on silent hangs; health-check requests get highest scheduling priority so they don't time out under load. Multimodal fix: switched Hugging Face PIL-based image processors to Torchvision-based and set OMP_NUM_THREADS to the container's vCPU count (not the host's) to stop CPU throttling.
- **Numbers**: Serves >125T tokens/month. Autoscaling on model units gave over 80% GPU savings vs static provisioning at peak. Full hang detect→kill→recover cycle <5 minutes; false liveness failures dropped from several per week to zero. Image processing (resize+normalize) is 10x slower than other CPU ops like base64 decode; example host 192 vCPUs vs container 12 vCPUs. After the Torchvision + OMP_NUM_THREADS fix, requests completed per second jumped >3x at same replicas and load.
- **Token-cost implication**: Model request cost non-linearly by input/output token distribution and hardware, not by request count; long-output requests are the expensive ones. Use sticky/load-aware routing to raise prefix-cache hit rates for agent workloads. Autoscale on a cost-derived utilization metric, not pending-request or CPU counts, to avoid over-provisioning. Pin container thread counts (OMP_NUM_THREADS) to the container, not the host.
- **Caveats**: Vendor engineering blog; all figures self-reported, measured on Databricks' own fleet/customers. The 80% saving is "at peak" for bursty-traffic models; the 3x is specific to the multimodal/image bottleneck. The model-unit cost function's exact form and coefficients are not disclosed.
