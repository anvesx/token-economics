# 076 — TokenLake: A Unified Segment-level Prefix Cache Pool for Fine-grained Elastic Long-Context LLM Serving
- **Source**: https://arxiv.org/abs/2508.17219 (arXiv / Peking University + StepFun, 2025-08)
- **Claim**: Existing cluster-level prefix caching is tightly coupled to request scheduling, causing load imbalance, cache redundancy, and memory fragmentation. TokenLake is a unified segment-level prefix cache pool with a declarative interface that decouples cache management from scheduling, improving throughput and hit rate for long-context serving.
- **Mechanism**: Prefix caches are split into fixed-size segments distributed across all GPU instances as one pool, with cache access decoupled from compute. A declarative interface exposes query tensors, prefix caches, and cache-aware ops (control plane: get_prefix_tree, get_cache_load, gen_plans; data plane: init_query, query, init_transfer, put). Three co-located engines (compute, query, transfer) run concurrently via NVIDIA MPS with CUDA IPC zero-copy shared buffers (q_buf, kv_buf) registered as NCCL network buffers. A heavy-hitter-aware segment-level load balancer hashes normal segments uniformly and selectively replicates the top O(N log N) heavy hitters (found via BFS near prefix-tree root) to least-loaded instances; replicas chosen via power-of-two-choices, evicted via global LRU. A bipartite-matching dispatcher (Hungarian algorithm, O(n^3) per iteration) minimizes communication volume. A goodput-optimized stateless elastic scheduler uses chunked prefill + PD disaggregation + elastic sequence parallelism via dynamic programming.
- **Numbers**: Throughput improvement up to 2.6x vs cache-aware routing (SGLang-Router) and 2.0x vs cache-centric PD-disaggregation (MoonCake); hit-rate boost up to 2.0x and 2.1x respectively. Production prefix-cache hit rates reported 75%–95% (CharacterAI, Kimi). Manus average input:output ratio 100:1; Character.AI avg 180 turns/session. Segment-size threshold C ≈ 568 tokens for their setup; communication overhead of a short decoding request with 1000 prefix tokens ≈ 4.66 µs/layer; Llama-7B decoding KV transfer = 16 KB/request/layer. Query-tensor comm volume ≈ 2dlN_p. Prototype = 16k LoC. Hardware: 8× A100 80GB, 128 CPUs, NVLink 400 GB/s, 4×200 Gbps InfiniBand, CUDA 12.4, NCCL 2.24.3; model LWM-1M-Text Llama-2-7B, TP=2. Datasets: LooGLE (avg 24K seq), SCBench (avg 227K seq, avg 5 turns), ShareGPT (<2.4K). TokenLake CV stays below 15% (avg 11%) vs SGLang-Router 99% (9x higher), MoonCake-1P3D 62% (5.63x), MoonCake-3P1D 122% (11.09x). P90 goodput gains: LooGLE 2.08x/2.04x vs MoonCake variants (4.46x/3.32x at equal input-token latency), 2.55x vs SGLang-Router; SCBench MoonCake served only ~20% of requests under SLO; ShareGPT 3.71x/1.56x. Pooling: TokenLake-1P3D/3P1D latency 26.62–86.05x and 2.18–39.48x lower than MoonCake variants; elastic reduces latency up to 5.22x/2.82x. Multi-node (16× A800 80GB, 2 servers, 1:1:1 mix): throughput 5.47x/28.49x/5.46x higher than MoonCake-6P2D/2P6D/SGLang-Router.
- **Token-cost implication**: At cluster scale, prefix-cache management and request scheduling should be decoupled via a declarative, segment-level memory pool so all GPU memory/bandwidth is used as one cache — eliminating replication of shared system prompts and shared documents, reducing recomputation, and raising hit rate. Builders serving long-context/multi-turn workloads can cut serving cost by pooling KV cache rather than per-instance prefix trees with cache-aware routing.
- **Caveats**: Self-reported by the authors; prototype evaluated on A100/A800 clusters with a single 7B model (LWM/Llama-2-7B) and three datasets. TokenLake itself consumes some GPU resources for cache management (exposed via get_cache_load). Gains depend on fast interconnect (NVLink/InfiniBand) and the segment-size threshold derived for their hardware. No test of larger models or other hardware; baselines limited to SGLang-based solutions for fair comparison.
