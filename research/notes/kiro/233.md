# 233 — LLM Cost Management: Track and Control Spend (Langfuse)
- **Source**: https://langfuse.com/resources/engineering/llm-cost-management (Langfuse, no date)
- **Claim**: LLM cost management is a four-layer practice — track, attribute, control, optimize (in that order) — and most cost surprises are measurement errors, so accurate per-token tracking must be fixed before any optimization.
- **Mechanism**: Four layers: (1) Track — record every call exactly once with mutually-exclusive token buckets and the price in effect at run time; cost either ingested from the provider response (authoritative, preferred) or inferred from token counts × a model price list (ingested always wins in Langfuse). (2) Attribute — propagate `user_id`, `session_id`, tags/metadata, and environments at trace time so cost breaks down per user/session/feature/tenant/model/prompt version (invoices never carry your keys). (3) Control — threshold alerts on cost metrics over rolling windows (Slack/webhook/GitHub Actions), hard budgets/rate limits enforced at the gateway, and spend alerts on the observability bill itself. (4) Optimize — route by task difficulty, use prompt caching as its own priced bucket, trim context, cap loops/retries; consider reserved inference capacity (e.g. Morph) for sustained high-volume. Pricing tiers model context-dependent rates (condition like input>200000, evaluated in priority order, default tier otherwise). Model matching via regex `match_pattern`; user custom definitions take priority over the built-in list.
- **Numbers**: As of July 2026, Anthropic Claude Sonnet 4.5 and Google Gemini 2.5 Pro charge higher prices when a request exceeds 200K input tokens. Langfuse Python SDK v4+ and JS/TS SDK v5+ apply a default span filter dropping non-LLM spans. Example overstatement: OpenAI-style `prompt_tokens` includes cached tokens while Anthropic `input_tokens` excludes cache reads (inclusive counts stored as-is double-count cache reads). No savings percentages given.
- **Token-cost implication**: Fix measurement before optimizing: pick one reporting path per request (prefer the application SDK over gateway logs, which carries more context) to avoid double-counting; store mutually-exclusive token buckets (subtract cached/detail counts from top-level counts exactly once before ingesting flat keys; strip any extra key a gateway appends to the usage object or OpenAI-schema recognition silently treats it as flat); add a custom model definition whose regex matches the exact model string your traces report (Bedrock reports inference-profile IDs/ARNs; gateways add/strip provider prefixes; fine-tunes carry suffixes); model tiered pricing explicitly so >200K-token requests are not underpriced; filter non-LLM OTel spans so the observability bill is not inflated. Audit by grouping cost by model name and flagging entries with usage but zero cost.
- **Caveats**: Vendor content (Langfuse) describing its own product capabilities; no independent measurement or benchmark, no quantified savings. Inferred cost is computed at ingestion time with prices known then, so later price fixes apply only to new generations (historical traces stay as-costed). Partial model-name matches can be worse than no match (silent wrong price).
- **Topic**: observability
