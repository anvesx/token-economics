Abstract—Public leaderboards rank large language models
(LLMs) in general, but an engineer has to choose a model for a
specific application, architecture and cost. This paper presents
a method for application-specific capability profiling of LLMs
and its realization as a containerized testbed. The method
treats each application as a unit of extension: an
Oracle-to-PostgreSQL
migration
agent,
a
documentation-grounded chatbot or an enterprise-support
automation agent runs in its own container behind a small
contract, brings its own dataset, evaluator and owned
attributes, and is onboarded together with its dashboards.
Measurements accumulate in a versioned, sparse metamodel of
every model. The method separates the model under test from
judges and agents, freezes and hashes plans, refuses to compare
values from different contexts, diagnoses the instrument before
the system, and applies a null-agent check and a noise rule
whose operating characteristics are quantified by simulation.
In the evaluated automation conditions, model choices
produced larger differences on selected observable outcomes
than framework choices, although the experimental design
does not establish a general causal ranking of these factors. The
experiments also show that instruction tuning is
deployment-specific and that system-reported success can
exceed independently observed success: of 216 migration units
checked against a real Oracle database, 108 were demonstrably
correct. These measurements establish application-specific
observations, not a universal model ranking.
Keywords—large language models, capability profiling,
model selection, metamodel, diagnostics, benchmarking, testbed,
Grafana, LLM agents, database migration

I.​

INTRODUCTION

Choosing a large language model (LLM) for an
enterprise application is still, in most teams, an exercise in
reading leaderboards and trusting vendor claims. Public
benchmarks such as MMLU [1], BIG-bench [2], HELM [3]
and Chatbot Arena [4] answer the question “how good is
this model in general?”, but an engineer who has to migrate
a legacy database, operate a documentation assistant or
automate a support queue asks a different question: “how
good is this model for this task, in this architecture, at this
cost?” The two questions diverge more than is commonly
assumed. In our own experiments a configuration change
that improved intent classification by 4.6 percentage points
on one deployment lowered it by 3.4 points on a second and
had no effect on a third, so that a tuning result measured on
a weak deployment described the deployment rather than the
prompt. Similarly, in an automation agent that reasons over
Jira, Confluence and Outlook events, the choice of the
model changed the amount of work actually performed
(mean state-changing effects per run) between 0.5 and 1.8,
while the choice of the agent framework moved the same
quantity only between 0.4 and 0.7.
This paper presents a method for application-specific
capability profiling of LLMs and the containerised testbed
that realises it. The method is designed to make such
differences visible, measurable and comparable. It profiles
LLMs by running them through reference applications:
small but complete prototypes of the application classes that
matter to the authors’ organisation, namely an

Oracle-to-PostgreSQL
migration
agent,
a
documentation-grounded chatbot and an enterprise-support
automation agent. Every application is packaged as a
separate container with an evaluation interface. The testbed
executes models against datasets and application
configurations, records versioned measurements, and
exposes them through an analytical interface and through
Grafana dashboards. The accumulated measurements form a
sparse, versioned metamodel of each LLM: a profile of
attributes, each measured in the same way for every model,
which can be queried to decide which model should do
which task at what cost.
The method is organised in eight steps, from defining an
application and onboarding it to deciding on a model and
monitoring the profile (Section IV). Its central design
decision is that an application is a unit of extension of the
testbed, not just a workload. When a new application is
added, it brings its own dataset, its own evaluator and its
own attribute declarations, and onboarding registers the
application in the probe registry, in the metric catalogue and
in the dashboards. As a consequence the set of LLM features
that the testbed can talk about grows with the set of
applications it hosts: a chatbot adds retrieval and citation
attributes, an automation agent adds tool-use and side-effect
attributes, a migration agent adds behavioural-equivalence
attributes. Section V describes the mechanism; Section VIII
reports what the first three applications have revealed,
together with a simulation of the decision rule and a
statistical re-analysis of the reported counts.
A.​ Problem Statement and Research Questions
We study the following problem. Given a growing set of
LLMs and a growing set of application classes, build an
experimental infrastructure that (i) measures every model on
every application under controlled and fully recorded
conditions, (ii) keeps the measuring instrument separate
from the object measured, (iii) refuses to report numbers that
were produced under different conditions as if they were
comparable, and (iv) makes the result usable for model
selection. The work is organised around four research
questions.
●​ RQ1. What architecture allows heterogeneous
reference applications to be added to an
LLM-profiling testbed without modifying its core,
while
preserving
reproducibility
and cost
transparency?
●​ RQ2. Which measurement and diagnostic principles
are necessary so that the numbers produced by such a
testbed can be trusted, given that agents, judges and
applications are themselves LLM-driven, and how
should a failure be diagnosed: in the instrument first,
or in the system?
●​ RQ3. What do the first three reference applications
reveal about the dependence of model behaviour on
task, configuration and framework?
●​ RQ4. How can the accumulated measurements be
turned into a decision aid for model selection, and
which claims must it refuse to make?
B.​ Contributions
The paper makes six contributions. First, it states a
method for application-specific capability profiling in eight
steps (Section IV).

Second, it formalises an LLM metamodel as a sparse
partial function from attributes to measurements with
explicit context and plan identity, and defines the
comparability relation, the evidence levels and a capability
taxonomy used throughout (Section III).
Third, it presents the architecture of the testbed with its
application-container contract, onboarding algorithm,
deterministic plan gate, three-way cost separation and
dashboard registration, and it provides a reference
implementation of the computational core (Section V).
Fourth, it describes three reference applications and their
evaluation stands in sufficient detail to be reproduced
(Section VI).
Fifth, it states the measurement and diagnostic principles
distilled from defects that the authors found in their own
stands, including the instrument-first diagnostic ladder, the
degenerate-agent check and a three-state noise rule whose
operating characteristics are quantified by Monte Carlo
simulation (Section VII).
Sixth, it presents the measured results, their statistical
re-analysis, and the resulting evidence and capability maps
(Sections VIII and IX).
The methodological contribution is the operational
coupling
of
context-aware
measurement classes,
evidence-constrained verdicts and instrument-first diagnosis
with extensible application probes. The measured evidence
is preliminary and does not establish a universal ranking of
models or a causal ordering of model and framework effects.
The paper distinguishes measurement validity,
repeatability, and generalisability. Some comparisons
involve small or single-run samples, and some outcome
measures lack complete behavioural ground truth; these
boundaries are identified in the experiments and Section
IX-J. The study produces conditional capability profiles
rather than a context-free ranking of evaluated models.
The remainder of the paper is organised as follows.
Section II reviews related work. Section III formalises the
problem. Section IV states the method. Section V describes
the testbed architecture. Section VI presents the reference
applications. Section VII states the evaluation and diagnostic
methodology. Section VIII reports experiments and Section
IX discusses them. Section X concludes.
II.​

RELATED WORK

We reviewed 88 scholarly sources, including
peer-reviewed publications and preprints, and organised the
literature into six areas: general-purpose benchmarking,
application-level evaluation, LLM-as-a-judge, benchmark
validity and statistical analysis, cost-aware model selection,
and engineering practices for observable machine learning
systems. Table I summarises how the testbed relates to each
line.
A.​ General-Purpose Benchmarks and Holistic Evaluation
Large multi-task suites measure broad knowledge and
reasoning. MMLU [1] and AGIEval [5] use
examination-style questions, BIG-bench [2] collects
hundreds of community-contributed tasks, and HELM [3]
argues for holistic reporting over many scenarios and seven
metric families, including calibration, robustness and
efficiency, rather than accuracy alone. Human-preference
platforms such as Chatbot Arena [4] and judge-based
protocols such as MT-Bench [6] complement static suites
with open-ended comparisons. Surveys [7] show that the

2

evaluation literature is dominated by such general-purpose
protocols. Behavioural testing in the CheckList style [8] and
dynamic benchmark construction [9] address the fragility of
static test sets. These works define what to measure in
general; the testbed adopts their emphasis on multiple
metrics and on explicit scenarios, but replaces the “scenario”
with a complete reference application so that the measured
quantity is the behaviour of a model inside an architecture.
Two lessons from this line of work shape the testbed
more than any specific benchmark. The first is that a single
aggregate score hides the structure of model behaviour:
HELM reports accuracy next to calibration, robustness,
fairness, bias, toxicity and efficiency for the same scenarios
precisely so that trade-offs become visible [3], and
BIG-bench documents tasks on which scale alone does not
produce a smooth improvement [2]. The second is that
preference-based and judge-based protocols inherit
properties of their instruments. Pairwise voting at scale is
informative about open-ended chat quality [4], yet it cannot
say whether a model completes a database migration
correctly, and a benchmark that ranks models on
examination questions says little about their behaviour
inside a retrieval pipeline. For these reasons the testbed does
not attempt to compete with general leaderboards; it
assumes that a team has already shortlisted models from
them and asks what happens next.
B.​ Application-Level Evaluation: Retrieval, Agents, Code,
SQL
Retrieval-augmented generation [10] is evaluated with
component-level retrieval metrics on benchmarks such as
BEIR [11] and with generation-level criteria such as
faithfulness and answer relevance in automated frameworks
[12], [13]. RGB [14] diagnoses noise robustness, negative
rejection and information integration, and positional effects
in long contexts are documented in [15]. Dense retrieval
[16] and rank fusion [17] are the building blocks of the
retrieval configurations that our chatbot stand compares.
Agent evaluation has moved from single-turn function
calling [18], [19] to interactive environments: AgentBench
[20], WebArena [21], GAIA [22] and SWE-bench [23] score
the end state or the task outcome in realistic environments,
and surveys catalogue architectures and evaluation practices
[24], [25]. Reasoning-and-acting loops [26], self-reflection
[27] and experience-based learning [28] are the mechanisms
around which many agents are built, while multi-agent
frameworks [29], [30] supply orchestration patterns that we
treat as an experimental variable. Our automation stand
follows the end-state logic of these benchmarks but adds a
distinction that they rarely make explicit: whether a claim of
success in the final answer is backed by an observable
effect.
For code and data tasks, Spider [31] and BIRD [32]
evaluate text-to-SQL by execution, TransCoder [33] and
CodeTransOcean [34] address program translation, and
EvalPlus [35] shows that weak test suites overstate
functional correctness. A study of bugs introduced during
LLM-based code translation [36] and two broad surveys of
LLMs in software engineering [37], [38] frame the
migration problem. Classical text-similarity metrics such as
BLEU [39] and chrF [40] are still used as reference-based
signals, but our migration results, like [35], indicate that a
reference-based or acceptance-based verdict can overstate
correctness; execution against the source system is the
stronger instrument.

What these application-level works share is that they
evaluate a task in a fixed environment. For retrieval, the
environment is the corpus and the index; for agents, a web
or code environment; for SQL, a database. The
application-level testbed generalises the idea in two
directions. It treats the environment as one of the things that
can be versioned and registered (the dataset version and the
configuration are part of every measurement), and it makes
the claim–effect distinction explicit: AgentBench and
WebArena score the end state, but an agent that reports
success without an observable effect is not separately
counted in them, whereas in our automation stand the share
of such runs is itself an attribute. The same reasoning
applies to code translation: the studies of translation bugs
[36] show that models introduce subtle semantic differences,
and our finding that a clean install proves little is the
database-specific form of the EvalPlus lesson that weak tests
overstate correctness [35].
C.​ LLM-as-a-Judge
Judge models scale open-ended evaluation [6], [41],
[42], yet they exhibit position and verbosity effects [43] and
favour their own generations [44]. Our stands therefore use
judges only for criteria that cannot be computed
deterministically, keep them in a separate role from the
model under test, and measure their instability directly: in
the migration direction a semantic judge changed its verdict
on 16.2% of repeated items at temperature 0.
Leakage-resistant evaluation of judges on specifications [45]
and execution-judged benchmarks [46] are earlier results
from the same group that inform the design of the judge
roles.
Judge-based evaluation has a further cost dimension that
is rarely reported: the judge’s own spend. In the P1 stand,
1,802 combined judge calls cost more than twice as much as
the conversion of the same files, which is why the testbed
accounts for it separately. Learned judges such as
Prometheus [42] and structured prompting such as G-Eval
[41] improve agreement with human raters but do not
remove the dependence on the instrument, and the evidence
of self-preference [44] suggests that the judge should come
from a different family than the model under test whenever
the comparison is between vendors. In our chatbot stand
both the judge and the controller currently use the same
model family as one of the compared models, a limitation
we record in Section IX-J.
D.​ Benchmark Validity, Contamination and Statistics
The testbed reduces contamination exposure through
versioned, application-specific test data and isolation of
expected outcomes. Synthetic or private datasets alone do
not guarantee freedom from data contamination; that
remains an evaluation-specific threat to validity.
The statistical literature points in one direction: with few
items and few repeats, effects smaller than the noise cannot
be established. Dror et al. recommend matching the test to
the data and reporting the variability of the evaluation itself
[53], and Card et al. show that typical NLP comparisons
have too little power to detect the differences they report
[54]. Contamination studies add that the same model may
have seen the test items, so that a high score can be memory
rather than capability [49], [50]. The testbed responds in two
ways. Versioned private and synthetic application datasets,
together with the separation of ground-truth labels from
model inputs, reduce contamination exposure. However,
these safeguards do not establish that evaluation data are
entirely absent from model training or development

3

histories. For the variability, it declines to publish model
numbers until repeats have established the spread, and it
applies the coarse noise-floor rule of Section VII-F where a
formal test is not applicable.
E.​ Model Selection, Routing and Multi-Objective Trade-offs
Cost-aware use of LLMs has been studied as cascades
[59] and as quality-aware routing between a cheaper and a
stronger model [60]. Selecting among models with several
conflicting objectives is a multi-objective problem whose
standard solution concept is the Pareto set [61], [62]. The
analytical interface of the testbed computes Pareto sets over
measured attributes on the server and displays the evidence
count behind each claim; our migration agent uses a
deterministic complexity score for routing in the spirit of
[60], and our token-optimisation study [63] shows that cost
and quality must be evaluated jointly.
F.​ Engineering Practice for Observable ML Systems
Machine-learning systems accumulate hidden technical
debt [64], and rubrics for production readiness explicitly
include tests of data, model and infrastructure [65]. A case
study of software engineering for ML at scale [66]
documents the importance of data management and model
evaluation tooling. Programmable guardrails [67] and
prompt-programming frameworks [68] address safety and
prompt optimisation, respectively. Dashboards for
monitoring evolving information systems, including
ontology-driven platforms with dashboard-centric analytics,
have been investigated by co-author V. Lyashkevych
[69]–[73]. The risk perspective on LLM-based development
[74], the notion of a software functional state [75] and the
orchestration of multi-agent systems with dynamic
involvement of new agents [76] inform, respectively, the
security attributes, the lifecycle view and the extensibility of
the testbed. The metamodel idea itself builds on a unified
architecture metamodel for information systems generated
by AI [77]. Finally, a comparative analysis of frameworks
for the same three application classes [78] was the starting
point for the reference applications used here.
G.​ Prompt Programming and Reasoning Strategies
The behaviour of a model inside an application depends
on how it is prompted. Few-shot prompting [79],
chain-of-thought prompting [80] and interleaved reasoning
and acting [26] changed what models can do without
changing their weights, and declarative frameworks such as
DSPy [68] compile pipelines of model calls and optimise
their prompts against a metric. The testbed treats the prompt
variant as a registered, hashed object, requires a baseline
arm next to any compared variant and, in the programme
scheme, optimises prompts per probe so that a model is
measured under the prompt that suits it and the gain over the
baseline prompt is itself recorded. Our measurement that a
description rewrite had effects of opposite signs on three
deployments is consistent with the prompt-sensitivity
literature, and it adds a practical corollary: a prompt
optimised against one deployment is a property of the pair,
not of the prompt, so the optimisation target must be part of
the identity that is stored with the result. DSPy-style
optimisation against a metric also inherits the risk that the
metric rewards the wrong behaviour; the null-agent check of
Section VII-B is the guard that we apply before any loop is
pointed at a number.

H.​ Specification-Driven Development and Code
Regeneration
Specification-driven development treats a specification
as the operational artefact consumed by LLM development
agents. The authors’ earlier studies formalise a specification
as a structure of semantic blocks with dependency relations,
evaluate it with execution-judged benchmarks that keep the
implementer panel fixed and include a no-specification
control arm [46], evaluate the evaluators of specifications
under sealed ground truth [45], and show on database
migration that cost, validity and semantic preservation must
be traded off [63]. The generation hook of the testbed reuses
this machinery at a smaller scale: the application
specification is the artefact from which an adapter is
generated, and the smoke test and the control-arm discipline
are the checks that the generated adapter must survive. The
unified architecture metamodel [77] offers a representation
(JSON, PlantUML and Mermaid views of architectural
diagrams) that can serve as the structured context for such
generation.
I.​ Dashboards and Monitoring of Evolving Systems
Operational dashboards for ML systems are often built
last, as a view over logs. The earlier work of co-author V.
Lyashkevych on intelligent monitoring of evolving
information systems treats the dashboard as a first-class
element of the architecture, with ontology-driven domain
knowledge integrated into dashboard-centric analytics [69],
context-aware selection of decision strategies [70],
evolution-aware synthesis of monitoring systems by LLMs
[71], genetic optimisation of monitoring models for
LLM-modified systems [73] and multi-drift predictive
monitoring [72]. We adopt this stance: the dashboards of the
testbed are registered with the application at onboarding, not
added afterwards. A natural next step, discussed in Section
IX-D, is to monitor the metamodel itself for drift.

J.​ Intelligent Diagnostics, Knowledge Bases and Testing
The diagnostic stance of this paper has an older root in
the co-authors’ earlier research on intelligent diagnostics of
computer facilities, which treated diagnosing as a
knowledge-based task with its own infrastructure: an
ontology of the diagnostic subject domain [81], a software
tool for building the knowledge base of the diagnosing
process [82], retrieval of diagnostic information from
microprocessor devices [83], the search for features of
diagnostic information and the development of a search

4

service for it [84], [85], criteria for setting correspondence
between the terms of different knowledge bases [86], and
logic-textual and neural approaches to information search
[87]. Four ideas from this line carry over to the profiling of
LLMs. First, diagnosis needs an explicit subject-domain
vocabulary; in the testbed it is the attribute catalogue, in
which every attribute has an owner, a unit and a direction.
Second, diagnostic knowledge should be kept as a
knowledge base separate from the diagnosed system; the fix
ledger of the migration direction and the failure taxonomies
of the other directions play this role (Section VII-K). Third,
terms must be matched across knowledge bases with explicit
criteria; the same quantity appears as recall at K in one
probe and as a recall metric in another, and the catalogue
must decide when two names denote one attribute. Fourth,
retrieval of similar earlier failures is part of diagnosis, which
is the practical reason for storing per-unit outcomes and not
only aggregates.

Lemma 1 applies within a declared comparison design

The treatment dimension is declared in advance: models

identifiers and evaluator versions; a changed metric library
starts a new comparison class.

comparison with a human reference, and comparison with

level λ is only as strong as the weakest level at which every
unit that contributes to it was checked, and a report must

F.​ Scope and Assumptions
The testbed measures models, not applications: the
application is held fixed and the model is varied, or the
application configuration is varied while the model is held
fixed. The comparison of application architectures
themselves is the subject of a separate study [78]. All model
calls go through a single gateway, so that the models are
reached in a uniform manner and cost can be attributed to
the caller.

The programme that this work belongs to plans two
further stages, requirement analysis with specification
generation tailored to a chosen model, and specification
decomposition with decision making about which model
handles which part. They depend on stable profiles and are
outside the scope of this paper.

Three properties distinguish the method from a
benchmark run. The unit of evaluation is the application, not
the item. A leaderboard item is a question; a unit here is a
complete behaviour in an architecture, such as the migration
of a group of Oracle objects, a chatbot turn with its retrieval
and tool calls, or the handling of an enterprise event. The
artefact is a profile, not a rank. The result of the method is
the metamodel of a model: its measured attributes with their
contexts, and an explicit list of what was not measured. The
guards are part of the method. Each step carries a guard that
exists because a stand once misled its authors without it
(Table VII), and a result produced without its guards is
reported with a warning instead of a number. Table VIII
contrasts the method with a leaderboard on the dimensions
that matter to a team that has to choose.

G.​ Prompt Identity, Cost Accounting and Credentials
Three properties concern what is recorded about every
call. Prompt identity. The inherited P1 stand called its
templates directly and recorded nothing about the text sent
to the model, so every earlier run was, strictly,
unreproducible. Templates are now accepted as source
plus the identity under which they were registered; the
stand verifies that the source hashes to that identity and
binds only variables the mode provides, then records the
variant identifier and the hash on the run. Omitting a
prompt records the built-in under its own name and hash.

byte-identically to the old, so earlier results remain
comparable. Cost separation. The tested model, the judge

summed, because the first is a property of the model and

Decomposition. The parser splits each file into migration
units (table, view, sequence, function, procedure, package,
trigger, query or data-changing statement) while preserving
the original source text. A package remains one unit because
its members share state. Each unit carries a parse
confidence: full, partial, lexical-only or failed, and a low
confidence excludes the deterministic converter. Ordering.
A dependency graph places required objects before their
users; mutually dependent objects form one migration group
(a strongly connected component), and the condensation is a
directed acyclic graph that is processed in topological order.
A failing group blocks its dependants while independent
branches continue. The same decomposition idea underlies
the earlier study of task decomposition for specification
generation by the same team.
Routing. A deterministic weighted score in [0, 1]
estimates the difficulty of each group from source size,
control flow, data access, Oracle-specific features,
dependencies, cycles, package size and parse quality. Scores
up to 0.30 select the STATIC strategy (Ora2Pg and
deterministic rules, no model tokens), scores above 0.30 and
up to 0.65 select a cheaper model, and higher scores a
stronger model (Table XXII). Large packages go directly to
the strong model, and low analysis confidence promotes a
unit to a stronger strategy. Every routing decision records a
reason. The individual feature families of the complexity

B.​ Chatbot Agent: Documentation-Grounded Assistant
The chatbot is a developer-support assistant that answers
questions over a body of documentation, retrieving
passages, calling tools and citing sources. Its evaluation
framework measures how well different LLMs and chatbot
configurations work for documentation-based question
answering and where a failure occurs: in execution, tool
routing, retrieval, grounding or answer generation. It runs
the real chatbot with selected retrieval and model
configurations, scores it against a versioned dataset and
saves the evidence. Ground truth is never passed to the
chatbot; expected sources, tool behaviour and answer
content are used only by the evaluation engine. Its execution
and evaluation stages are summarised in Fig. 11.

Application, model, evaluation and experiment
configurations are stored separately, and every run saves the
configuration actually used. Six metric groups evaluate the
components separately (Table XXV); two methods are used.
Deterministic checks cover execution, tools, retrieval and
citation structure. A judge, semantic_judge_v1, scores
faithfulness, answer correctness, answer relevance and task
completion with fixed criteria; its scores support analysis
and comparison but do not by themselves decide PASS or
FAIL. The judge is an evaluation component built on an
existing LLM, not a separately trained model.

C.​ Automation Agent: Enterprise Support Tasks
The automation system handles inbound Jira,
Confluence or Outlook events with a single LLM agent that
reasons in a loop and acts through fifteen canonical business
operations, five per system. Every execution starts from a
fresh state, carries no memory from earlier executions, reads
knowledge without changing it and is bounded to ten steps.
Failures are typed outcomes, never hidden or fabricated. The
system has five layers (Fig. 13): entry points; strategy
selection; prompt orchestration, model-call interception and
tool management; business integrations, which are live
systems in production and a frozen world state in evaluation;
and infrastructure for configuration, retries, evidence and
authentication.
