                                                                                                     Abstract

                                                     In a multi-turn conversation, the choice of language model at one turn can affect
                                                     which model should answer the next. The selected model’s reply shapes the context
                                                     for the next query, and its cached prompt prefix can reduce the cost of using that
                                                     model again. We introduce MultiTurnRoute, a platform for building and evaluating
                                                     multi-turn LLM routers. A shared interface gives built-in and user-defined routers
                                                     the current query, dialogue history, and an estimate of each model’s reusable prefix
                                                     length. Our routing algorithm, Chain-of-Route (CoR), uses a learned gate over
                                                     recent and recurrent dialogue history to predict response quality and estimates
                                                     cost from each model’s reusable prefix. MultiTurnRoute Arena ranks routers on
                                                     recorded conversations and compares session quality and cost in interactive runs
                                                     where a simulated user responds to each reply. On a benchmark drawn from
                                                     WildChat and LMSYS-Chat-1M with per-turn quality annotations for five LLMs,
                                                     CoR reduces the normalized cost required to match the strongest model’s quality by
                                                     up to 20.3% relative to the strongest routing baseline, while matching or improving
                                                     peak response quality.

1        Introduction
A conversational assistant can draw on several large language models (LLMs), each with different
capabilities and inference costs. A router decides which model should answer a given query. Most
routers make this decision from the current input alone [1]. In an ongoing conversation [2], however,
a short follow-up can depend on several earlier turns. In WildChat [3], a corpus of 1M real user
interactions, 41% of conversations span multiple turns. Other conversation datasets show similar
patterns [4, 5]. Topics and user goals can also shift within a conversation [6, 7], so the model best
suited to one turn may be a poor choice for the next.
We introduce MultiTurnRoute, a platform for building and evaluating routers that select a model
at each turn (Figure 1). Its session runtime exposes two kinds of state through a common router
interface. The dialogue state helps a router interpret the query. The serving state tracks the prefix
each candidate model is expected to reuse. The selected model’s reply extends the dialogue, and its
token usage updates the cache record for the next decision.

Which prefix matters for cost? Serving engines such as vLLM [8] and SGLang [9] can reuse a
model’s cached key–value (KV) states for a shared prompt prefix. For example, the cited Claude
Sonnet prices are $3.00 per 1M input tokens and $0.30 per 1M cached tokens, a 90% reduction [10].
Each model may have answered a different subset of earlier turns and retained a different prefix. In
Figure 3, switching to a model with a lower nominal price costs more than continuing with the model
that already holds the session prefix.
Routing algorithm. Our router, Chain-of-Route (CoR), estimates quality and cost separately for
each candidate. Its Dialogue State Propagator (DSP) combines recent turns with a compact recurrent
history and learns how much context to use for each query. Its Serving State Tracker (SST) uses
each model’s cached prefix to estimate the cost of answering. On WildChat and LMSYS-Chat-1M,
CoR reduces Query-Normalized Cost (QNC), the minimum normalized cost required to match the
strongest model’s quality, by up to 20.3% relative to the strongest routing baseline, while matching or
improving peak response quality.
Evaluating routers. CoR, five built-in baselines, and user-defined routers implement the same
interface. MultiTurnRoute Arena uses that interface in two settings. Static replay compares choices
on the same recorded turns and ranks routers by their quality–cost trade-off. In interactive sessions, a
simulated user responds to the selected model’s reply, so an early routing decision can change the
questions a router faces later.

2     Background and Related Work

Multi-Turn LLM Conversations. Both conversational assistants and multi-agent systems make
successive LLM calls over shared context [2, 11, 12]. WildChat [3], ShareGPT [4], and LMSYS-Chat-
1M [5] document these interactions. Studies of topic shifts [6, 7, 13] and context dependence [14, 15]
help explain why different turns may call for models with different capabilities and costs [1, 16].
Existing conversation datasets [3–5, 17, 18] generally record a single model’s replies in each dialogue.
Routing benchmarks [19] provide quality labels for several models on individual queries. Evaluating
per-turn routing requires both dialogue histories and ratings for multiple candidate models on each
turn.
KV-Cache Management in LLM Serving. Successive prompts in a conversation share a prefix,
allowing an LLM to reuse key–value states from earlier turns [20, 21]. vLLM [8] manages these states
with paged allocation, SGLang [9] supports automatic prefix caching, and CachedAttention [22]
extends reuse by offloading states to host memory [23]. In the cited Claude Sonnet pricing, cached
input tokens cost 10% of the standard input price [10]. Each routing decision affects which model
accumulates reusable state. MultiTurnRoute tracks the reusable prefix length for each candidate, and
CoR uses it to estimate cost.
LLM Routing. Single-turn routers differ in how they predict model quality [1, 19, 24, 25] and
cost [26–30] (Appendix A). GMTRouter [31] learns user preferences across conversations and selects
one LLM for a session. Bao et al. [32] extend RouteLLM [1] to choose a model at each turn from
the full dialogue history. Their cost model distinguishes switching from staying with the last model.
CoR estimates how much of the prompt each candidate retains, including a model used several turns
earlier. Concurrent work, MTRouter [33], jointly encodes model embeddings and a token-limited
interaction history for agentic tool use. Its cost estimate uses token counts and list prices. The authors
also observe that switching models frequently can limit prompt-cache reuse.


3     The Chain-of-Route Algorithm

3.1   Overview: From Single-Turn to Multi-Turn Routing

Let M = {m1 , m2 , . . . , mK } denote a set of K candidate LLMs. At each turn t of a conversation,
the user submits a query Qt and the router selects a model mt to generate the answer At . The
router estimates each candidate’s response quality Q̂ and serving cost Ĉ, then selects the model that
maximizes the quality-cost tradeoff, where λ ∈ [0, 1] controls cost sensitivity:
                                             h                     i
                                 mt = arg max (1 − λ) · Q̂ − λ · Ĉ .                                 (1)
                                           m∈M

Equation 1 is the Lagrangian relaxation of maximizing response quality subject to a serving-cost
budget, with λ acting as the multiplier: sweeping λ over [0, 1] traces the quality-cost Pareto frontier,
and our metrics in Section 4 summarize this entire frontier rather than any single operating point. In
deployment, λ is a user-specified quality-cost preference, analogous to the effort levels exposed by
commercial assistants. Following recent single-turn routers [26, 28], we estimate quality and cost
separately. Decoupling the two estimates is natural here: KV-cache reuse avoids recomputing an
identical prefix, so it changes serving cost but not the response. This lets SST compute the cache
correction analytically while DSP focuses entirely on quality. Single-turn routers estimate Q̂ and Ĉ
based solely on the current query Qt : Q̂ = fQ (m, Qt ) and Ĉ = fC (m, Qt ). This does not account
for two forms of state that accumulate across turns in multi-turn conversations: the dialogue state,
i.e., the conversation history that shapes query meaning, and the serving state, i.e., the KV-cache
retained by each model’s serving engine that reduces serving cost.
We observe that each routing decision both depends on and shapes the state available to future
decisions. On one hand, the router must consult both forms of state to make an informed choice:
the dialogue state determines how to assess each model’s quality on the current query, while the
serving state determines each model’s true serving cost. On the other hand, the routing outcome
alters both states for subsequent turns: the selected model’s answer extends the dialogue history, and
its serving engine retains the KV-cache, reducing its serving cost if chosen again later. This means
routing decisions are inherently chained, with state propagating from one turn to the next.

3.2    Dialogue State Propagator (DSP)

As illustrated in Figure 2, routing based solely on the current query is context-blind (a), feeding the
full history introduces context overshadowing (b), and selectively retrieving relevant history misses
implicit dependencies (c). Rather than conditioning on raw dialogue at each turn, DSP maintains a
compact hidden state Ht that incrementally accumulates conversation-level information (e.g., topic
evolution and cross-turn dependencies) through a learned recurrent update [34, 35]. This decouples
the router from the raw dialogue while preserving the contextual signals necessary for accurate quality
estimation.
DSP decomposes Ht into two complementary components: a local history state Htℓ ∈ Rd that
captures fine-grained, recent context (e.g., the current topic and turn-level difficulty), and a global
history state Htg ∈ Rd that captures coarse-grained, conversation-level trends (e.g., overall user
expertise and long-term topic distribution). The concatenated state Ht = [Htℓ ; Htg ] is used at each
turn to inform the routing decision, then updated with the new query-answer pair before propagating
to the next turn.
DSP maintains two states that are read before routing each turn and updated only after the selected
model generates its answer. Concretely, when routing turn t, DSP consults the buffer Bt−1 and global
state Htg produced after turn t−1, computes a fresh local state Htℓ from Qt and Bt−1 , forms the
dialogue state Ht = [Htℓ ; Htg ], and feeds Ht together with Qt to a context-dependency gate that
controls how much history reaches the quality estimator. After At is generated, a frozen pretrained
sentence encoder E (all-MiniLM-L6-v2 [36], d=384) produces d-dimensional embeddings of the
new pair, which we denote Qt , At ∈ Rd (overloading the textual symbols), and concatenates them as

Context-dependency Gate. Not all queries in a multi-turn conversation depend equally on prior

new topics and can be routed independently. This suggests that the router should adaptively decide
how much history to incorporate for each query, rather than applying a fixed strategy. With Htℓ
and Htg in hand, DSP forms the dialogue state Ht = [Htℓ ; Htg ] and computes a context-dependency
gate αt ∈ [0, 1] that assesses whether the current query requires conversational context, as shown in

4.1   Experimental Setup

Model pool. We evaluate CoR and the comparison methods on a shared pool of K=5 models. The
Arena protocols are described separately in Section 5. The experimental pool comprises Qwen3-0.6B,
Qwen3-8B, Qwen3-14B, Qwen3-32B, and Qwen3-Next-80B-A3B-Instruct. We take each model’s
full-prefill price cm                              m
                    prefill and generation price cgen from publicly listed OpenRouter pricing, and set
                               m           m
the cached-input price as ccached = 0.2 cprefill following Alibaba Cloud Model Studio’s context-cache
convention.1 The full per-model pricing table is in Appendix C.
Dataset. Existing multi-turn dialogue benchmarks [5, 17, 18] are single-model and do not provide
per-turn multi-model quality scores; we therefore construct evaluation data from WildChat [3]
and LMSYS-Chat-1M [5]. From each corpus we randomly sample 20,000 English conversations
(∼80,000 turns) with ≥ 2 turns per conversation, and split 80/20 by conversation hash.
To train the quality predictor, we need per-(turn, candidate) quality labels. We obtain them by having
every candidate model m ∈ M generate a response for every training turn t under the same dialogue
history, using the dataset’s original responses for prior turns:
                                                     orig                 orig
                         contexttrain (t) = {(Q1 , A1 ), . . . , (Qt−1 , At−1 ), Qt }.                (10)
Each candidate response is independently scored on a 1–10 scale by DeepSeek-V3.1, selected from a
panel of candidate judges via meta-evaluation against human ratings [18] (details in Appendix B).
We adopt this shared-context construction as a tractable offline protocol: faithfully enumerating all
routing trajectories scales as |M|T in the conversation length, which is intractable. These quality
scores supervise DSP. A separate head predicts output length from observed response lengths. SST
combines this prediction with the tracked prefix length and token prices to estimate cost (Appendix D).
At evaluation, each routing strategy follows one trajectory per held-out conversation. For each
user query in that conversation, CoR uses DSP and SST to select a model under Equation 1. Each
comparison method uses its own decision rule. The selected model generates a reply, which DeepSeek-
V3.1 judges and which becomes part of the history for the next query.
Baseline Methods. Random selects uniformly per turn. Single-turn routers RouteLLM [1], CAR-
ROT [28], and CSCR [27] route each turn from the current query alone. Multi-turn routers Bao
et al. [32] (full-history input + binary switch penalty) and GMTRouter [31] (cross-conversation
user graph) are the closest competitors. The Myopic Oracle in Figure 7 (a) is a per-turn hindsight
oracle: along its own trajectory, it picks the candidate maximizing Equation 1 using judge-assigned
quality and realized cost under the current states, without branching over future decisions (O(KT )
per λ, not O(K T )). All learned routers share all-MiniLM-L6-v2 [36] as the text encoder; training
hyperparameters, λ grid, and baseline adaptations are in Appendix D.
Evaluation Metrics. We evaluate each routing strategy using a deferral curve [27, 37], which
plots the average per-turn response quality against the average normalized cost. Sweeping the cost-
sensitivity parameter λ over the interval [0, 1] (Equation 1) traces the deferral curve. Following [37],
we employ three evaluation metrics: (i) Area Under the Deferral Curve (AUDC), measuring the
overall quality-cost trade-off; (ii) Peak Quality, the maximum quality achievable by the router; and

the most capable LLM in the pool. Unless noted otherwise, ablations are run on WildChat with the
default configuration; a sensitivity analysis over CoR’s main design choices (local-history window,
global state architecture, text encoder, cache discount) is provided in Appendix F.

5     The MultiTurnRoute Platform
5.1   Session Runtime and Router Interface

MultiTurnRoute connects a conversational application to a pool of LLMs (Figure 1). At each turn a
registered router reads the current query, dialogue history, and the estimated reusable prefix length
for each candidate. It selects one model, and the runtime dispatches the request to its backend. The
backend (vLLM [8] or a provider API) returns the reply and reports billed and cached tokens when
available. The runtime records the exchange and updates the session state. Applications can use
an OpenAI-compatible endpoint, including deployments behind gateways such as vLLM Semantic
Router [38].
CoR and five built-in baselines (single-turn, full-history, RAG, kNN, and simplified Bao et al.)
implement decide(turn, state). A researcher can register another router with that interface and
use the same implementation in the runtime and Arena. The router can use either part of the state.
For example, a cache-aware policy can compare the cost of returning to a previously used model with
that of continuing on the current model. A history-based policy can use the same input to estimate
which model will answer a follow-up well. The runtime executes either choice and accounts for the
realized cost using the backend’s input, cached, and output token counts. This lets researchers change
the decision rule while using the same backend and accounting code. The implementation is available
at https://github.com/loopleap-lab/MultiTurnRoute.

5.2   MultiTurnRoute Arena

Single-turn arenas such as RouterArena [39] can look up a pre-scored answer for each query. In
a conversation, a model’s reply can also change what the user asks next. MultiTurnRoute Arena
measures these effects in two tracks.
Static replay. The static track uses 3,996 conversations drawn from the benchmark in Section 4. A
separate pool of nine models answered every recorded turn in its original context, and a judge rated


                                                     9
each answer. On the held-out split, the Arena looks up the rating of the model selected by the router.
All routers see the same user queries and recorded replies. Their costs can still diverge because each
router’s sequence of model choices determines which prefixes its models can reuse. The Arena holds
the model pool, prices, and cost weights fixed and ranks routers by area under the deferral curve
(AUDC). The leaderboard therefore compares policies within this pool. The main experiments in
Section 4 use their own model pool and quality annotations.
Interactive sessions. The dynamic track starts routers from the same task. A simulated user reads
the selected model’s reply and writes the next question or ends the conversation. An answer that
requests clarification, for example, can lead to a different sequence of later turns than an answer that
completes the task immediately. A judge rates each answer in its own dialogue context, and the Arena
computes cost from the token usage reported by the backend. Routers run on matched tasks with the
same model pool and user simulator. For each cost weight, the Arena averages answer quality and
normalized cost over rated turns and sums the billed cost across all turns.


6   Conclusion

MultiTurnRoute gives researchers a common interface for building multi-turn LLM routers and
comparing their decisions on recorded and interactive conversations. Our routing algorithm, Chain-
of-Route, uses DSP to estimate response quality from dialogue history and SST to estimate cost from
each model’s cached prefix. On WildChat and LMSYS-Chat-1M, CoR reduces QNC by up to 20.3%
relative to the strongest baseline while matching or improving peak response quality. Ablations show
that both modules contribute. MultiTurnRoute Arena lets researchers compare other routing policies
under the same conditions and examine how a model choice affects later turns.

A    Survey of Single-Turn LLM Routers

LLM routing has been widely adopted in open-source platforms [38, 40] and commercial deployments
such as OpenAI’s GPT-5 [41] and Azure AI Foundry [42]. Existing routers vary primarily in how
they predict per-candidate quality and cost, but uniformly treat each query in isolation.
Quality predictors. Lightweight models are trained to estimate each candidate’s response quality
via neural networks [1, 43, 44], k-nearest neighbors [19, 45, 46], and graph neural networks [24].
Cost predictors. Early routers rely on static attributes such as per-token pricing [26, 27], while
more recent work incorporates output-length prediction [28, 46, 47] for more accurate per-query cost
estimates.
Complementary routing signals. A separate line of work introduces complementary signals into
the routing decision while still routing each query independently: Arch-Router [48] aligns routing
with human preferences over latency-quality trade-offs, R2-Router [25] introduces reasoning into
the routing decision, HW-Router [29] and INFRAMIND [30] incorporate real-time hardware and
serving-system signals such as queue lengths, KV-cache usage, and recent latency to meet latency
SLOs, and past-performance retrieval [49] retrieves past performance records to generalize routing to
unseen models.
Safety-aware routing. Beyond quality and cost, foundation models [50, 51] raise safety and security
concerns. They are vulnerable to trojan and backdoor attacks that hijack their outputs through
hidden triggers [52–54] or bias their predictions against specific groups [55, 56], to poisoned retrieval
corpora in retrieval-augmented generation [57], and to adversarial text perturbations [58]. Tracing
the provenance of model-generated text calls for robust watermarking [59, 60], and protecting user
data during training and inference motivates cryptographic privacy-preserving computation [61–68]
and trusted execution environments [69]. Routing offers a natural point at which to enforce such
safeguards [70]: SafeRoute [71] routes each input between a small and a large safety guard model,
invoking the large model only on hard inputs to keep guardrail accuracy high at lower cost. Like the
routers above, it decides for each input independently.
None of the above account for dialogue or serving state across turns; CoR explicitly and jointly
models both. We compare against Bao et al. [32], which routes each turn of a conversation, as a
baseline.


B    Dataset Construction Details

Why existing multi-turn benchmarks are inadequate. MT-Bench [18] contains only 80 two-turn
dialogues, each completed by a single LLM. MT-Bench-101 [17] scales to 1,388 multi-turn dialogues
but remains single-model. LMSYS Chatbot Arena [5] provides large-scale human preferences at the
conversation level, not per-turn quality scores. None of these provides what per-turn routing requires:
for each turn t, quality scores Q(m, Qt ) from multiple candidate models under the same dialogue
context.
Preprocessing. For both WildChat and LMSYS-Chat-1M we apply identical preprocessing: filter
to English conversations with ≥ 2 turns and ≥ 10 characters per user query, then randomly sample
20,000 conversations (∼80,000 turns) per corpus.
Shared-context protocol for training-label construction. The shared-context design used to build
the per-(turn, candidate) training labels ensures: (1) fair comparison—all candidate models see
identical context at each turn, so quality differences reflect model capability alone; (2) tractability—it
yields K comparable labels per turn in O(KT ) generation and judge calls, without depending on
a particular routing policy; and (3) extensibility—adding a new model requires only generating
and scoring its responses without regenerating existing data. This shared-context construction is
restricted to label generation: at evaluation time we run auto-regressive routing, where each routing
strategy traces a single trajectory per held-out conversation and the routed model’s actual response
is fed back as context for the next turn, faithfully reflecting deployment conditions including any
response-distribution shift induced by routing-driven model switches.
LLM judge selection. To select a reliable LLM judge, we followed the LLM-as-a-judge validation
protocol [18]: we randomly sampled 500 candidate responses, and recruited a pool of 30 expert


                                                   16
annotators with each response receiving independent ratings from 3 annotators (yielding 1,500 human
ratings whose mean is the gold label). We then evaluated 4 candidate judges (DeepSeek-V3.1, Qwen3-
235B-A22B, GPT-5-mini, and Llama-3.3-70B-Instruct) by computing their Pearson correlation with
the gold labels. Among them, DeepSeek-V3.1 achieved the highest correlation (ρ = 0.84) and was
selected as the final judge. This LLM-as-a-judge approach is crucial for evaluating open-ended
dialogue queries, where traditional automatic evaluation methods such as exact match fail to capture
response quality.
Scoring details. Each model’s response at each turn is independently scored on a 1–10  scale. We
                                                                                    K
use individual (non-pairwise) scoring for scalability (K evaluations per turn vs. 2 for pairwise)
and compatibility with our quality predictor Q̂, which estimates absolute quality rather than relative
preference. Dialogue context is truncated to 1,000 characters per prior message to manage judge
token cost; this caps prompt length while preserving topical and stylistic cues that drive multi-turn
quality. Scores are returned in structured JSON format with reasoning.

D     Implementation Details

Encoder and training. All learned routers (CoR and baselines) use all-MiniLM-L6-v2 [36] as the
shared text encoder (d=384). Routing models are trained on the 80% training split with AdamW
(lr 1×10−4 , batch size 64, 20 epochs, early stopping on validation MSE). The training objective is
mean-squared error between predicted quality Q̂(m, Qt , Ht ) and the judge-assigned ground-truth
quality, summed across all K=5 candidates.
DSP configuration. The local-history window is W =2, and the global state dimension is d=384
(matching the encoder).
    2 https://www.alibabacloud.com/help/en/model-studio/context-cache

Cost normalization and λ sweep. We divide each turn’s raw cost (token-weighted by per-model unit
cost) by the maximum-model cost so that costs lie in [0, 1]. Output length per candidate is predicted
by a lightweight regression head following CARROT [28]: a per-candidate linear head on the same
MiniLM-L6 query embedding, trained on the 80% training split with mean-squared error against the
candidate’s actual response length and reused at routing time. We sweep λ ∈ {0, 0.05, 0.10, . . . , 1.0}
when computing the deferral curve.
Baseline adaptations. Bao et al. [32] originally route between two models with a binary switching
penalty; we adapt their formulation to our five-model pool by treating each pairwise switch under
the same penalty schedule. GMTRouter [31] originally learns per-user preferences from cross-
conversation histories; we instantiate it by treating each conversation hash as a distinct user, using
the authors’ reference implementation. History-strategy variants (Query-only, Full History, RAG
Retrieval) share CoR’s encoder and training pipeline but differ in how they construct the input to the
quality predictor. Full-history + SST baselines feed the concatenated dialogue history to CARROT,
CSCR, and IRT-Router, keep each router’s own quality predictor, and replace its cost estimator with
CoR’s SST. The BERT full-history variant fine-tunes a BERT-base encoder (109.5M parameters)
end-to-end on the full dialogue history.
Component ablation training. To ablate DSP or SST individually, we re-train CoR with the
corresponding module replaced by its single-turn or cache-unaware counterpart while keeping the
other module unchanged.


E    Compute Resources

Routing module training. CoR’s routing modules consist of a frozen all-MiniLM-L6-v2 encoder
(∼22M parameters, kept fixed) plus lightweight per-candidate task heads. Each training configuration
trains for at most 20 epochs over the 80% training split with batch size 64 and completes in under 2
hours on a single NVIDIA A100 (40GB) GPU. The full sensitivity sweep (Appendix F: window W ,
global-state architecture, encoder, cache discount; Appendix G: pool size K; Appendix H: eviction
rate pevict ) totals roughly 30 training runs and approximately 60 GPU-hours.
Candidate-response generation. Generating per-(turn, candidate) responses across the five Qwen3
models on ∼160K turns (WildChat + LMSYS-Chat-1M) is performed via the OpenRouter API.
The resulting shared-context responses are generated once and can be reused for training. Held-out
evaluation generates the replies selected along each routing trajectory.
LLM-judge scoring. DeepSeek-V3.1 scores each shared-context candidate response on a 1–10 scale.
This one-time labeling cost scales with |turns| × K. The same judge scores replies generated during
held-out evaluation. The judge meta-evaluation (500 samples × 4 candidate judges, Appendix B) is a
small fraction of the total judge spend.
Evaluation. Auto-regressive evaluation runs each routing strategy as a single end-to-end trajectory
per held-out conversation. Per-strategy evaluation across the held-out test split with |λ|=21 values
completes in under 1 hour on the same A100 GPU; total wall-clock is dominated by candidate
inference latency rather than the routing decision itself, which is sub-millisecond per turn.

I.1   Robustness to the LLM Judge

Our main experiments use DeepSeek-V3.1 both to construct training labels and to score evaluation
trajectories, which raises the concern that a learned router could exploit judge-specific preferences.
We therefore evaluate two cross-family configurations in which the training judge (used to re-label the
training set and re-train all methods) and the test judge come from different model families; no model
responses are regenerated. The test judge never sees the training labels. As shown in Table 8, method
rankings and the relative gaps between methods are preserved. Together with the human-anchored
judge selection in Appendix B (ρ=0.84 against human gold labels), this indicates that the observed
gains are not explained by sharing a judge between label construction and evaluation.

I.2   Stability of the Recurrent State across Dialogue Depth

A recurrent state could in principle drift over long conversations. Table 9 reports quality-prediction
MSE by turn depth. DSP remains stable from turns 1–2 to turns 8+ (0.094 → 0.088), as does
Global-only (0.128 → 0.127), whereas Query-only degrades substantially (0.154 → 0.193). We find
no evidence of state drift.

J     Limitations

Pool excludes proprietary frontier models. Our main pool consists of open-weight Qwen3 models,
with cross-family checks using Llama-3.1 and Mistral. State-of-the-art proprietary models such as
Claude Opus, Claude Sonnet, and Claude Haiku are not included, even though production routers in
practice often mix open-weight and proprietary endpoints. Incorporating such models would broaden
the quality-cost frontier the router operates over and is a natural next step. Our commercial-billing
experiment (Appendix I.4) already includes lightweight and mid-tier Claude and Gemini models.
Domain-specialized candidates. Evaluating explicitly domain-specialized candidates (e.g., medi-
cal [72] or legal LLMs) requires only per-turn labels for them and no change to CoR.
Cache retention under load. Measuring cache retention in a local multi-model deployment under
sustained load is left to future work.


K     Broader Impacts

CoR is a routing layer over publicly available LLMs and does not generate content itself, so most soci-
etal impact accrues to the underlying models rather than the router. We highlight three considerations
specific to CoR’s operating regime.


                                                            22
Efficiency and access. By exploiting KV-cache reuse and cost-aware model selection, CoR can reduce
per-conversation serving cost and energy, which may broaden access to high-quality conversational
LLMs at lower price points and lower carbon footprints per query.
Routing-induced exposure. If the router systematically prefers particular candidates for particular
query types, any biases, factual errors, or failure modes of those candidates are amplified for users
issuing those query types. Deployers should monitor per-model behavior across the realized routing
distribution, not only models in isolation, and consider auditing routing decisions for fairness across
sensitive query categories.
Privacy and cache isolation. SST consumes KV-cache state from the serving engine across turns
of the same conversation. Operators should ensure cache isolation across distinct user sessions (a
default property of vLLM and SGLang under standard configurations) so that cache reuse cannot
leak information across users; CoR itself adds no new persistence beyond what the serving engine
already maintains.
